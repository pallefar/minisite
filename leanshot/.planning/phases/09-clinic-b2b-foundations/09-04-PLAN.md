<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous browser → /clinic-invite/lookup | Untrusted token in URL; hash compared server-side; lookup response carries org metadata (intentional disclosure to the invitee) |
| patient browser → supabase.auth.signUp (State D) | Supabase Auth UNIQUE(email) is the single-identity serializer (Pitfall #1) |
| patient browser → acceptInviteExisting RPC | RPC re-validates token hash + email match between auth.users.email and invites.email (Plan 09-01 RPC) |
| client-side sha256 of invite token | Hash function runs in browser; token still in URL (intended ephemeral exposure) — same risk as Phase 8 share token |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-23 | Tampering / spoofing | duplicate auth.users via race (Pitfall #1) | mitigate | InviteSignupForm routes through supabase.auth.signUp; on "already registered" error transitions to State C |
| T-09-24 | Replay | token reused after acceptance | mitigate | Plan 09-01 accept_invite_* RPCs UPDATE accepted_at + consumed_at; subsequent lookup returns State F |
| T-09-25 | Information disclosure | logged-in user clicks invite for different email | mitigate | accept_invite_existing RPC asserts lower(auth.users.email) = lower(invites.email); on mismatch → error_42501; UI surfaces 'email_mismatch' error toast |
| T-09-26 | Information disclosure | invite metadata leaks org existence to anonymous attacker who guesses tokens | accept | 128-bit token entropy makes brute-force infeasible; rate-limit on lookup endpoint (Plan 09-06) backs this up |
