### B1 — Plan 03 Task 1 + Task 2: `motion/react` and `motion/react-m` import paths do not resolve under installed `framer-motion@^11.11.17`

**Severity:** BLOCKER (only fires if Wave 3 runs, but Wave 3 IS gated, so the blocker is conditional — still must be fixed before any execution because the plan as written will not typecheck or build)

**Location:**
- `02.1-03-PLAN.md` lines 91, 111, 115, 116, 138, 174-175, 252-256
- Specifically the `<action>` of Task 1 instructs `import { LazyMotion, domMax } from 'motion/react';`
- And `<action>` of Task 2 instructs `import * as m from 'motion/react-m';` plus `import { AnimatePresence } from 'motion/react';`

**Evidence:**
```
$ grep -E "\"(framer-motion|motion)\":" leanshot/package.json
    "framer-motion": "^11.11.17",
```
The `motion` package (the new Motion brand entry point that exposes `motion/react`, `motion/react-m`) is **not installed**. It is a separate npm package (motion@^12) that did not exist in `framer-motion@^11.x`. Under `framer-motion@^11.11.17`, the equivalent imports are:
- `import { LazyMotion, domMax, m, AnimatePresence } from 'framer-motion'` (all from the same package)
- The `m` lazy primitive is exported as a named export from `framer-motion` itself.

The plan's "fallback" sentence in Task 1 step 5 ("if needed, fall back to `import { LazyMotion, domMax } from 'framer-motion'`") and Task 2 step 8 ("the fallback safe path is to import from framer-motion's namespace exports if motion/react-m is not available") is non-mechanical — it asks the executor to discover the failure at typecheck time, then make a judgment call. RESEARCH §C1 itself uses `motion/react-m` syntax (lines 711, 728-729), so the planner inherited the failure from RESEARCH.

**Why this is a blocker:** if Wave 3's gate fires, the executor will run Task 1 / Task 2 verbatim. `npm run typecheck` will fail (`Cannot find module 'motion/react-m'`). The executor will then either:
(a) fall back per the loose hint and end up with a working but completely different import shape than the SUMMARY-required diff format, OR
(b) try `npm install motion`, introducing a new dep that is OUT OF SCOPE per Standard Stack (RESEARCH line 616: "No new libraries should be added in 2.1 unless option (c) C1 ships (LazyMotion is part of the existing framer-motion package — no new install)" — RESEARCH explicitly says the install IS in the existing package).

The plan internally contradicts itself: line 67 states "`framer-motion` package stays in `package.json` (LazyMotion is part of the same package; no install change)" but the action body imports from `motion/*` paths that don't exist in `framer-motion@^11`. This is a self-contradiction the planner must resolve.

**Required fix:**
- `02.1-03-PLAN.md` Task 1 `<action>` step 2: change `import { LazyMotion, domMax } from 'motion/react';` to `import { LazyMotion, domMax } from 'framer-motion';`
- `02.1-03-PLAN.md` Task 2 `<action>` step 2: change the import recipe to either of:
  - Single-line: `import { LazyMotion, m, AnimatePresence, useDragControls } from 'framer-motion';` (named exports, all from one package)
  - OR explicitly note v11 vs v12 forking: "If `framer-motion` is upgraded to ^12 in a future PR, the `motion/react-m` paths become available; until then use the v11 named exports."
- `02.1-03-PLAN.md` `<interfaces>` block (lines 86-119): rewrite the example imports to match the v11 surface.
- `02.1-03-PLAN.md` `must_haves.truths[0]` (line 25): rewrite to reference `import { m, AnimatePresence } from 'framer-motion'` (or whatever the chosen path is).
- `02.1-03-PLAN.md` `must_haves.key_links[1]` (lines 44-47): rewrite the `pattern: "from 'motion/react-m'"` to match the v11 path.

### B2 — Plan 04 `depends_on: ["02.1-01"]` plus its `needs:` graph hides a Wave-1-only-deploy gap

**Severity:** BLOCKER

**Location:** `02.1-04-PLAN.md` line 6 (`depends_on: ["02.1-01"]`, wave 4) AND `02.1-05-PLAN.md` line 6 (`depends_on: ["02.1-01", "02.1-02", "02.1-03", "02.1-04"]`, wave 5).

**The structural problem:** Plan 02 (Wave 2) and Plan 03 (Wave 3) are CONDITIONAL — they may be skipped per the measurement gate. Plan 02's `<wave_gate>` (lines 99-110) reads "Wave 5's lhci 3-run on the post-Wave-1 Preview reported median Performance < 0.90" — so Wave 5 must measure FIRST, then Wave 2 conditionally fires, then Wave 5 measures AGAIN. But Plan 05's `depends_on: ["02.1-01", "02.1-02", "02.1-03", "02.1-04"]` says Wave 5 runs ONCE, after all other waves. **The dependency graph is acyclic in the abstract, but the wave-gate semantics demand a measure-then-decide loop that the DAG cannot express.**

This isn't just style — it's an executable gap. If `/gsd-execute-phase` walks the DAG bottom-up:
- Wave 1 (Plan 01) lands the function-form fix
- Wave 2 (Plan 02) is supposed to wait for Wave 5's measurement, but Wave 5 depends on 02 → Wave 2 has no measurement to gate against
- Result: executor either skips Wave 2 unconditionally (worst case — never knows if (a) sufficed) or runs Wave 2 unconditionally (defeats the "stop at the first step that gets to 0.90" ROADMAP directive)

This contradicts ROADMAP.md line 76-79 ("Re-measure after each step; stop at the first one that gets to 0.90") and RESEARCH §"Recommended order of operations" (which describes a per-wave measurement gate, not a single end-of-phase measurement).

**Required fix (mechanical):** Restructure the wave graph to model the measurement loops explicitly. Two acceptable shapes:

Option A (split Wave 5 into measurement-gates + final sign-off):
- Wave 1: 02.1-01 (function-form fix) — unconditional
- Wave 1.5: NEW measurement plan 02.1-01-MEASURE (deploy + lhci) — depends_on: ["02.1-01"]
- Wave 2: 02.1-02 (modulepreload) — depends_on: ["02.1-01-MEASURE"], with explicit wave_gate reading 02.1-01-MEASURE's output
- Wave 2.5: NEW measurement plan 02.1-02-MEASURE — depends_on: ["02.1-02"]
- Wave 3: 02.1-03 (LazyMotion) — depends_on: ["02.1-02-MEASURE"]
- Wave 4: 02.1-04 (CI fixes) — depends_on: ["02.1-01"] (correct as-is — independent of measurement loops)
- Wave 5: 02.1-05 (final sign-off + docs) — depends_on on whichever measurement plan was the "successful" one + 02.1-04

Option B (collapse measurement into each conditional plan's Task 0 — cheaper):
- Plan 02 gets a new Task 0 "Deploy current main + run lhci 3-run; if median ≥ 0.90 STOP and write skip-SUMMARY; else proceed to Task 1."
- Plan 03 gets the analogous Task 0.
- Plan 05 keeps `depends_on` on all four but tolerates skip-SUMMARYs from 02 and 03.

Option B requires fewer files and matches the existing `<wave_gate>` block style; Option A is more explicit and easier to audit. Either fixes the gap. Pick one and commit.

**Documentation note:** Plan 02 line 105 says "Mark the plan as 'skipped per measurement gate' in the SUMMARY and proceed directly to Wave 5" — this language tells the executor to handle the loop manually outside the DAG. That's a recipe for forgetting one of the rungs. The DAG should encode the loop, not narrate it.

## Warnings

### W1 — Plan 04 chunk-size threshold (30 kB gz) is too loose to catch the original Phase 2 regression class with margin (audit point #9)

**Severity:** WARNING

**Location:** `02.1-01-PLAN.md` line 129 ("Threshold: `30000` bytes gzipped") + RESEARCH §"Code Examples" same number.

**Reasoning:**
- Phase 2 ship: vendor-react = 3,009 bytes gz (carries only `scheduler`)
- Predicted post-fix: vendor-react = 50,000-60,000 bytes gz (RESEARCH §"Predicted post-fix sizes")
- Threshold 30,000 sits midway — well above 3 kB (catches the original regression) but FAR below the post-fix floor.

The threshold is in the *correct direction* (catches the regression class) but is too loose to catch a 50%-regression. Example: if a future PR causes react-dom to re-collapse PARTIALLY (e.g., react-dom-server stays in vendor-react but react-dom/client falls back into index because of a static-import refactor), the chunk could drop to ~20-25 kB gz. The 30 kB threshold catches that. But if vendor-react stays at 35 kB while losing critical pieces, the assertion silently passes.

Recommendation: either
(a) After Wave 1 lands and the actual post-fix size is measured, raise the threshold to `(actual_size - 10000)` for tighter guarding, OR
(b) Add a SECOND assertion: `[ "$INDEX_SIZE" -lt 50000 ]` (index chunk shouldn't grow back above ~50 kB gz). The two assertions together pin the topology rather than just the lower bound on one chunk.

This is a WARNING because the threshold IS adequate for the original regression; tightening is defense-in-depth. Document the rationale in 02.1-BUNDLE-MEASUREMENT.md (Plan 05 already plans Section 6 carry-forward notes — add this).

### W2 — Wave 4 (Plan 04) does not wait for the post-Wave-1 build to confirm the assertion is GREEN before adding it to CI

**Severity:** WARNING

**Location:** `02.1-04-PLAN.md` Task 2 "Local dry-run" instruction (line 257) is the only real gate — and the CI step's first PR run is the actual proof.

**Risk:** if the executor runs Wave 4 in parallel with Wave 1 (both have `depends_on: ["02.1-01"]` → 04 has only that, 01 is itself), and the function-form fix has a typo or regex bug that yields a vendor-react chunk of 28 kB instead of 50 kB, the CI step lands but immediately fails the next PR. This is recoverable but noisy.

But explicitly bump this to a `<wave_gate>` note: "Wave 4 must run AFTER Wave 1 has produced a green local assertion run; if Wave 1's local build does not satisfy the assertion, do NOT add the CI step — return to Wave 1." The current text relies on the executor inferring this from the `depends_on` ordering.
