# Phase 02.1 Plan 01: Function-Form manualChunks (Vendor-React Fix) Summary

Converted `vite.config.ts` `manualChunks` from object form to function form so that `react-dom` (and the rest of the React core) actually lands in `vendor-react` instead of being folded into the entry chunk. Landed a CI-grade chunk-size assertion script BEFORE the fix so it failed-red against the current Phase 2 build, then turned green after the fix.

---

## Pre-fix vs. post-fix gzipped sizes (verbatim from `gzip -c | wc -c`)

| Chunk | Pre-fix (Phase 2 ship, object form) | Post-fix (Phase 2.1, function form) | Delta |
|-------|--------------------------------------|--------------------------------------|-------|
| `dist/assets/vendor-react-*.js` | **3,009 bytes gz** (`vendor-react-Dvy8yi29.js`, 7.75 kB raw — scheduler only) | **60,491 bytes gz** (`vendor-react-D-1Pq-3n.js`, 193.81 kB raw — react + react-dom + scheduler) | **+57,482 bytes gz** |
| `dist/assets/index-*.js` | **69,572 bytes gz** (`index-CyWYoN1r.js`, 222.59 kB raw — included react-dom) | **14,442 bytes gz** (`index-Bl3stJWq.js`, 45.20 kB raw — entry only) | **−55,130 bytes gz** |
| Net | 72,581 bytes gz | 74,933 bytes gz | +2,352 bytes gz total |

Total cold-path bytes are slightly larger (+2.3 kB gz) because the dictionary-savings effect from the all-in-one `index` chunk is partially lost when react-dom is split out. Per RESEARCH §"Predicted post-fix sizes", the win is in **parallel fetch + parser cost**, not raw bytes. Lighthouse's FCP/LCP scoring weights time-to-interactive heavily; a 60 kB chunk parsed in parallel with a 14 kB chunk beats a 70 kB chunk parsed serially. Wave 5 will measure the actual Lighthouse delta on a Vercel preview.

Predicted-vs-actual reconciliation:
- Predicted vendor-react: 50–60 kB gz → **actual 60.5 kB gz** (top of band, within prediction)
- Predicted index: 25–35 kB gz → **actual 14.4 kB gz** (BETTER than predicted — Vite's chunking heuristic moved more out of the entry than RESEARCH expected; net more code-splitting wins)

```
::error::index chunk is 69572 bytes gzipped (ceiling 50000) — likely react-dom or other vendor code collapsed back into entry. See .planning/phases/02.1-spa-lighthouse-perf/02.1-RESEARCH.md

```

**Both guards fired** as predicted by RESEARCH. The vendor-react FLOOR alone would have caught the catastrophic ~3 kB Phase 2 regression; the index CEILING alone would have caught it from the other direction. Having both is redundant by design — the ceiling pins the topology so a future partial-collapse regression (where vendor-react stays in the band but index regresses) is also caught (Plan revision 1, W1 in 02.1-PLAN-CHECK.md).

### Modulepreload status — Wave 2 likely SKIPPED

`dist/index.html` after the fix carries:

```html
<script type="module" crossorigin src="/assets/index-Bl3stJWq.js"></script>
<link rel="modulepreload" crossorigin href="/assets/vendor-react-D-1Pq-3n.js">
<link rel="modulepreload" crossorigin href="/assets/vendor-icons-B9etE6DE.js">
<link rel="modulepreload" crossorigin href="/assets/vendor-motion-DA_X2pGV.js">
<link rel="modulepreload" crossorigin href="/assets/vendor-telemetry-D_6hX5kF.js">
```

**Vite is auto-emitting `<link rel="modulepreload">` for all four vendor chunks** that are now reachable via the entry's static graph — including the freshly-promoted `vendor-react-*.js`. Per RESEARCH §"What Vite already emits", this is exactly what would otherwise have required a manual `transformIndexHtml` plugin in Wave 2. Per the Wave 1 → Wave 2 gate in the plan:

> Wave 2 only proceeds if Wave 5's lhci median Performance < 0.90 AND inspection of the deployed `index.html` shows Vite did NOT auto-emit `<link rel="modulepreload" href="/assets/vendor-react-*.js">`.

The second condition has flipped to FALSE — Vite did auto-emit it. So **Wave 2 is unconditionally SKIPPED regardless of the lhci result.** If Wave 5 lhci is < 0.90, the executor should jump directly to Wave 2.5 diagnose / Wave 3.

### Tighten-the-floor follow-up

Actual measured vendor-react size: **60,491 bytes gz**. Per the wave_gate carry-forward, Wave 5 (Plan 05) should propose tightening the floor to **50,000 bytes gz** (actual − ~10,000) for tighter regression guarding. The current 30,000 floor catches the catastrophic Phase 2 regression class (3 kB) with ~10x headroom; the proposed 50,000 floor would catch a ~17% regression class (e.g., a future PR accidentally splitting react-dom out of vendor-react into its own micro-chunk).
