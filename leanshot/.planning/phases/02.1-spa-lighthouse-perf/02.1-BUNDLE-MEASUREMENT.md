## Why each lever moved (or didn't move) the needle

### Wave 1 — function-form `manualChunks` (no perf change)

Object-form `manualChunks` only moves a module into a named chunk if it's STATICALLY imported from the entry's static graph. `react-dom` was only imported by `main.tsx` directly, so it stayed in `index`. Function-form `manualChunks: (id) => /node_modules\/(react|react-dom|scheduler)/.test(id) ? 'vendor-react' : ...` evaluates per-module and forces all matching modules into the named chunk.

Bundle topology was correct after Wave 1, BUT Performance was unchanged because the actual cold-load bottleneck was elsewhere — see "telemetry defer" below.

### Telemetry defer (commit `bf517f6`) — +0.07 perf

Phase 2's `main.tsx` had `import * as Sentry from '@sentry/react'` and `analytics.ts` had `import posthog from 'posthog-js'` — both static. That dragged `vendor-telemetry` (93 kB gz combined) onto the entry static graph, where Vite auto-emits `<link rel="modulepreload">` for it.

Fix in `src/lib/telemetry-defer.ts`: schedule `import('@sentry/react')` and `initAnalytics` (which now does `import('posthog-js')` internally) at `requestIdleCallback` (or 100ms timeout fallback). Phase 1 D-12 error-capture floor preserved by a tiny `error`/`unhandledrejection` buffer that drains once Sentry resolves.

Effect: `vendor-telemetry` left the modulepreload set entirely. Critical-path preloaded bytes: ~210 kB → ~118 kB gz (-44%).

### Font CSS non-blocking (commit `7ea9a9d`) — +0.11 perf

The Google Fonts CSS link was render-blocking (default `<link rel="stylesheet">` semantics — even with `display=swap` in the URL, which only governs the FONT FILES, not the CSS). FCP couldn't drop below the CSS download time.

Fix in `index.html`: Filament Group preload-as-style + print-onload swap pattern. Browser fetches the CSS in parallel with HTML parse; loads it as `print` media (non-blocking); JS swaps `media='all'` on load. `<noscript>` fallback for crawlers.

Effect: FCP dropped 3.0s → 2.1s; LCP dropped 3.6s → 2.4s.

## What's still on the modulepreload critical path


`vendor-motion` is still preloaded because something in App's static import graph (likely `Toast` / `AppShell`) statically imports framer-motion. If a future phase pushes Performance back below 0.90 and TBT moves above 200ms, the LazyMotion migration recipe in `02.1-03-PLAN.md` is ready to execute — would shave ~30 kB gz off the preload set.

## Tighten-the-floor follow-up (W1 forward-link)

Plan 01's chunk-size assertion currently enforces vendor-react ∈ [30, 80] kB gz. Actual post-fix size: **60.5 kB gz**. Tighten the floor to `actual - 10 kB = 50 kB` in a follow-up commit so accidental partial-regression (e.g., dropping react-dom from the chunk again) is caught even when the chunk stays above 30 kB. The ceiling (80 kB) is fine — gives ~33% headroom for legitimate React API additions before triggering.

(Not landed in this commit — a tighten beyond the original 30 kB floor changes the assertion's tolerance band, which is a separate decision worth its own commit/PR.)

## Reproduction

```bash
SPA_URL="https://leanshot-app.vercel.app"  # or any SPA preview URL
mkdir -p /tmp/lhci && cd /tmp/lhci && rm -rf .lighthouseci
npx --yes @lhci/cli@0.15.1 collect --url="$SPA_URL" --numberOfRuns=3
for f in .lighthouseci/lhr-*.json; do
  python3 -c "import json,sys; d=json.load(open(sys.argv[1])); c=d['categories']; print('perf=%.2f' % c['performance']['score'])" "$f"
done
```
