## Why object-form `manualChunks` didn't pull react-dom into `vendor-react` (root cause)

**TL;DR:** The root cause asserted in `02-HUMAN-UAT.md` E1 ("react-dom collapsed back into `index`") is **directionally correct but mechanistically wrong**. Object-form `manualChunks` *did* try to assign react-dom to `vendor-react`, but the resulting chunk became unreachable from the entry's static graph because **every consumer of React in `src/` is loaded via `React.lazy(...)`**. Rollup obeyed the directive, then optimizer logic pruned the static-graph link to `vendor-react` because nothing statically imported react-dom from any chunk it knew was on the entry critical path.

### Direct evidence from the current `dist/`

Built locally on commit `70c3085` (no source changes since the Phase 2 ship):

```
dist/assets/vendor-react-Dvy8yi29.js : raw=7,749   gz=3,009
dist/assets/index-BQin493k.js        : raw=222,548 gz=69,543
```

Inspecting `vendor-react-Dvy8yi29.js`:
- File contents start with `import{a as J}from"./vendor-telemetry-7I1EDKys.js";var H={exports:{}},I={};/** @license React scheduler.production.js ...`
- It contains **only** the React `scheduler` package (~3 kB gz) and a tiny re-import.
- `grep -c "createRoot\|hydrateRoot\|react-dom/client"` against `vendor-react-*.js` → **0**
- `grep -c "createRoot\|hydrateRoot\|react-dom/client"` against `index-BQin493k.js` → **1** (the entry's `createRoot(document.getElementById('root')!)` call)

`vendor-react-Dvy8yi29.js` is **listed in `__vite__mapDeps`** at the top of `index-BQin493k.js` — the array Vite uses to enumerate chunks that should be modulepreloaded *when a dynamic import is triggered*. That's the smoking gun: Vite treats `vendor-react` as a chunk reachable only via dynamic import, not as a static-graph entry dependency. Therefore Vite emits *no* `<link rel="modulepreload">` for it on cold load — it sits behind the first `React.lazy(...)` boundary that needs scheduler, which fires after `index-*.js` parses and React renders.

Net result on cold load:
1. Browser fetches `index-*.js` (69.5 kB gz) — this contains react-dom in full. **Confirmed by `grep -c "react-dom"` returning 2 occurrences and the file containing `createRoot` from `react-dom/client`.**
2. Browser parses `index`, calls `createRoot`, mounts `<App>`.
3. `<App>` triggers `React.lazy(() => import('@/components/marketing/Landing'))`.
4. That dynamic import resolves the dep tree which finally references `scheduler` — Vite *now* fetches `vendor-react-Dvy8yi29.js` (3 kB).
5. So the *named* chunk has only scheduler, react-dom rode along in `index`, and the projected ~107 kB savings never materialised.

### Why the object form behaves this way (the canonical Rollup semantics)

Per Rollup's official docs on `output.manualChunks` `[CITED: rollupjs.org/configuration-options/#output-manualchunks]`:

> "each property represents a chunk that contains the listed modules and **all their dependencies if they are part of the module graph** unless they are already in another manual chunk"

Two clauses bite us:

1. **"if they are part of the module graph"** — react-dom must actually be reached from somewhere. It IS reached (from `main.tsx`'s `createRoot` import), so this clause passes.
2. **"unless they are already in another manual chunk"** — react-dom is *also* a transitive dependency of every lazy-loaded chunk. In practice Rollup's chunking algorithm has to decide: keep react-dom in the named `vendor-react` and have it re-imported by `index` at runtime, OR inline it into the entry chunk that statically imports it.

The third bite is the [VERIFIED] observation that Vite (with `build.modulePreload.polyfill: true` default) emits the `__vitePreload` helper and a `__vite__mapDeps` array — **and also performs static-graph optimization that can absorb a "vendor" chunk into an entry chunk if the entry is the only static consumer**. Phase 2's `main.tsx` is the only place that statically imports `react-dom/client` (every other React consumer is lazy-loaded), so Rollup decided: "react-dom is a singleton, the entry needs it eagerly, fold it in."

**Independent confirmation from the ecosystem:**
- `vitejs/vite` issue #12209 ("Using manualChunks breaks code-splitting") — multiple users report that object-form manualChunks does not behave intuitively when entries and lazy chunks share a common dependency. `[CITED: github.com/vitejs/vite/issues/12209]`
- Mykola Aleksandrov's 2025 post "Taming Large Chunks in Vite + React" walks the *exact* same scenario (React app with lazy routes, react-dom collapsing into the main bundle); his fix is the function form. `[CITED: mykolaaleksandrov.dev/posts/2025/11/taming-large-chunks-vite-react/]`
- Kowalczyk's "vite/rollup manualChunks" TIL post documents the same semantics — object form is "convenient but lossy"; function form is "verbose but predictable". `[CITED: blog.kowalczyk.info/til-vite-rollup-manualchunks.html]`
- vitejs/vite removed `splitVendorChunkPlugin` in v6 explicitly because the object-form pattern it emitted was problematic in real apps; the migration recommendation is function-form `manualChunks`. `[CITED: github.com/vitejs/vite/pull/19255]`

### Why the HUMAN-UAT note's framing matters less than the fix

The UAT note says "react-dom collapsed back into `index`". That phrasing implies a Vite bug. The actual mechanism is: **react-dom never moved to `vendor-react` to begin with — it stayed in `index` because the entry statically imports it and the lazy graph that should have re-used `vendor-react` was satisfied by the entry-bundled copy.** The fix is the same; the framing matters because it tells the planner *what to verify after the fix*: not just that vendor-react grew (it will), but that `index-*.js` *shrank* by approximately the same amount.

## Function-form `manualChunks`: canonical pattern + pitfalls

The unanimous recommendation across current Vite/Rollup ecosystem sources `[CITED: vite.dev/config/build-options, rollupjs.org/configuration-options/, mykolaaleksandrov.dev 2025-11, blog.kowalczyk.info]`:

```ts
// vite.config.ts → build.rollupOptions.output.manualChunks
manualChunks(id: string): string | undefined {
  // CSS-module guard (RESEARCH gotcha — manualChunks receives ALL ids
  // including CSS module ids; returning a chunk name for a .css id can
  // break the CSS pipeline)
  if (id.endsWith('.css')) return undefined;

  if (id.includes('node_modules')) {
    // React core — react, react-dom, react-dom/client, scheduler.
    // Match on the path segment so a package named "react-foo" doesn't
    // accidentally land here.
    if (
      /node_modules\/(react|react-dom|scheduler)(\/|$)/.test(id)
    ) {
      return 'vendor-react';
    }
    if (
      /node_modules\/(framer-motion|motion-dom|motion-utils)(\/|$)/.test(id)
    ) {
      return 'vendor-motion';
    }
    if (/node_modules\/(chart\.js|@kurkle\/color)(\/|$)/.test(id)) {
      return 'vendor-charts';
    }
    if (/node_modules\/lucide-react(\/|$)/.test(id)) {
      return 'vendor-icons';
    }
    if (
      /node_modules\/(@sentry\/react|@sentry\/core|@sentry\/browser|@sentry-internal\/browser-utils|posthog-js)(\/|$)/.test(id)
    ) {
      return 'vendor-telemetry';
    }
    // Any remaining node_modules → fall through to Vite's automatic
    // chunking (use cases: zustand, @use-gesture/react). Returning
    // undefined preserves the current behavior of "Vite decides".
  }
  return undefined;
}
```

**Why anchored regex (`/node_modules\/react(\/|$)/`) instead of `id.includes('react')`:** the simpler `id.includes('react')` matches `node_modules/preact`, `node_modules/react-foo`, even `src/components/cards/StreaksCard.tsx` (path contains "react" via the project name "leanshot/.../react" — actually no, not here, but the principle holds). The Mykola Aleksandrov post uses `id.includes('react') || id.includes('react-dom')` and it's the most widely cited pattern, but it's slightly fragile. We have `@use-gesture/react` in `package.json`; with `id.includes('react')` that package would land in `vendor-react`, which is wrong (it's not a React-core dep, it would invalidate the cache-stable vendor-react chunk on every @use-gesture release). The anchored regex avoids this. `[VERIFIED: package.json:23 lists @use-gesture/react ^10.3.1]`

### Known pitfalls of function form

1. **CSS-module ids leak through.** `[CITED: web search 2025 patterns]` Always guard with `if (id.endsWith('.css')) return undefined;`. Without the guard, you can accidentally route CSS into a JS chunk and Vite will complain.
2. **pnpm path layout.** Not relevant here — `package-lock.json` confirms npm, not pnpm. `[VERIFIED: leanshot/package-lock.json present, lockfileVersion: 3]`
3. **Asset ids (SVG via `?url`, etc.).** The function receives those too. The regex-against-`node_modules/` guard naturally filters them out (assets aren't in `node_modules/`). No additional guard needed.
4. **`undefined` return = Vite default.** Returning `undefined` is the correct way to opt OUT of manual chunking for a given id (lets Vite's heuristic decide). Returning `''` or `null` is undefined behavior — don't.
5. **Don't forget the marketing entry's React.** The marketing build (`vite.marketing.config.ts`) does NOT define `manualChunks`. Per the 02-07 SUMMARY, default chunking is fine because `marketing-*.js` is 106 kB gz total and marketing scored ~1.00. **Do not add manualChunks to the marketing config in 2.1.** `[VERIFIED: dist-marketing/assets/marketing-*.js present, 106 kB gz per 02-07 SUMMARY]`
6. **Keep the comment that tags D-23.** The current `vite.config.ts:48-65` references `02-02-BUNDLE-MEASUREMENT.md` and the human-approved decision. The function-form rewrite must preserve that audit trail (extend the comment, do not delete it).
7. **Rolldown migration on the horizon.** Vite 8 is moving to Rolldown which only supports function-form `manualChunks` (and is moving toward `advancedChunks`). `[CITED: github.com/voidzero-dev/vite-plus/issues/900]` Function form here is also the future-proof choice.

## Modulepreload for hashed assets in vite (concrete patterns)

Vite already does *some* of this automatically. Understanding what it already does is critical to deciding whether option (b) is needed at all.

### What Vite already emits (out of the box)

Per Vite docs `[CITED: vite.dev/config/build-options]`:

- `build.modulePreload` defaults to `{ polyfill: true }`. The polyfill is auto-injected into each entry's HTML.
- For the **entry's static-import graph**, Vite emits `<link rel="modulepreload" href="/assets/<hashed>.js">` tags into `index.html` automatically.
- For **dynamically imported** chunks (anything reached via `import('./foo')`), Vite emits a `__vite__mapDeps` array + a `__vitePreload(...)` helper inside the calling chunk. When the dynamic import fires at runtime, the helper appends a `<link rel="modulepreload">` to the document head for each dep just before fetching.

**What this means for our `index.html`:** Open the deployed Phase 2 build's `index.html` — Vite has already emitted `<link rel="modulepreload">` tags for `index-*.js` and any of its **static** imports. But because `vendor-react` is currently treated as a *dynamic* dep (per `__vite__mapDeps`), it does NOT appear as a static `<link rel="modulepreload">`.

**After the function-form fix:** when `react-dom` actually moves into `vendor-react`, the entry's static graph will include `vendor-react` (because `main.tsx` statically imports `react-dom/client`). At that point Vite will *automatically* emit `<link rel="modulepreload" href="/assets/vendor-react-<hash>.js">` into `index.html` with no manual work. **Step (b) may be unnecessary if (a) is done correctly.** This is the single most important insight in this research — the planner should NOT default to writing a custom `transformIndexHtml` plugin until measurement proves (a) alone fell short.

`[VERIFIED: Vite docs explicitly state automatic modulepreload generation for entry static-graph imports; current dist/index.html confirms vendor-react is in __vite__mapDeps not in static <link> tags]`

### If step (b) IS needed (modulepreload for hashed asset)

Three options ranked by simplicity:

#### Option B1 — Custom `transformIndexHtml` hook in `vite.config.ts` (recommended)

Zero new dependencies. Uses Vite's official plugin API.

```ts
// vite.config.ts plugins array — adds AFTER react() / tailwindcss(), BEFORE sentry plugin
function emitVendorReactPreload(): PluginOption {
  return {
    name: 'leanshot-emit-vendor-react-preload',
    apply: 'build',
    transformIndexHtml: {
      // 'post' so we run after Vite's own HTML transforms (which may already
      // have added modulepreload links). 'pre' would race against them.
      order: 'post',
      handler(html, ctx) {
        // ctx.bundle is populated only at build time, not during dev.
        if (!ctx.bundle) return html;
        // Find the hashed vendor-react chunk emitted this build.
        const vendorReactChunk = Object.values(ctx.bundle).find(
          (c) => c.type === 'chunk' && c.fileName.startsWith('assets/vendor-react-'),
        );
        if (!vendorReactChunk) return html; // dev/preview without the chunk; bail.
        const href = `/${vendorReactChunk.fileName}`;
        // Don't double-inject if Vite already added it (happens when (a) lands
        // and react-dom flows into the entry's static graph).
        if (html.includes(`href="${href}"`)) return html;
        const link = `    <link rel="modulepreload" href="${href}" />`;
        return html.replace('</head>', `${link}\n  </head>`);
      },
    },
  };
}
```

Notes:
- `transformIndexHtml` is documented in Vite's plugin API. `[CITED: vite.dev/guide/api-plugin]`
- The `ctx.bundle` field gives access to all emitted chunks with their final hashed filenames — no need to read the manifest.
- The `order: 'post'` + dedupe check makes this safe to ship even if (a) alone makes Vite emit the link automatically; it becomes a no-op in that case.

#### Option B2 — `vite-plugin-preload` npm package

Third-party. Last published recently per `vite-preload` package. `[CITED: github.com/wille/vite-preload, npmjs.com/package/vite-plugin-preload]` Adds an extra dep for what Option B1 does in 25 lines. Not recommended unless we have other modulepreload needs — we don't.

#### Option B3 — Generate manifest + read it server-side

Vite supports `build.manifest: true` which emits `dist/.vite/manifest.json` mapping `src/main.tsx → assets/index-<hash>.js + chunks: [...]`. `[CITED: vite.dev/config/build-options]` This is for SSR / backend-integration use cases; for a static SPA it's overkill. Skip.

### Pitfall: Vite's `build.modulePreload.resolveDependencies` (red herring for 2.1)

Vite has a `build.modulePreload.resolveDependencies(filename, deps, { hostId, hostType })` callback that lets you filter or augment the deps Vite preloads for *each dynamic import*. `[CITED: vite.dev/config/build-options]` This sounds like the right tool — it isn't. It only fires per dynamic import, and only modifies the runtime `__vite__mapDeps` arrays. It does NOT add static `<link>` tags to `index.html`. Don't use it for this purpose.

default-src 'none';

### Which CSP directive governs `<link rel="modulepreload">`?

Per the CSP spec and MDN `[CITED: developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Security-Policy/script-src]`:
- `<link rel="modulepreload">` is governed by `script-src`. The browser treats a modulepreload as a script fetch (because what it preloads is a JavaScript module), and CSP enforcement uses `script-src` for the URL check.
- Our `script-src 'self'` allows any same-origin script. Hashed assets at `/assets/vendor-react-<hash>.js` are same-origin (served from the same Vercel deployment). **No change needed.**

### Independent confirmation from real-world cases

- The Angular CLI bug report on modulepreload + CSP (issue #26330) `[CITED: github.com/angular/angular-cli/issues/26330]` confirms `script-src` is the directive enforced. The Angular issue was about *nonces*: when a CSP uses `script-src 'nonce-...'` instead of `'self'`, modulepreload links must also carry the nonce. We use `'self'` (not nonce-based), so we're unaffected.
- WordPress plugin scripts CSP thread `[CITED: wordpress.org/support/topic/content-security-policy-and-the-plugin-scripts-2/]` reports the same: modulepreload is a script source.

### One potential CSP gotcha unrelated to modulepreload

Worth flagging because it's adjacent: the Phase 2 UAT log noted a `vercel.live/_next-live/feedback/feedback.js` CSP violation on Preview deploys (cosmetic, Preview-only). That's NOT a modulepreload issue — it's Vercel's own injected feedback widget being blocked by `script-src 'self'`. Out of 2.1 scope; tracked in 02-HUMAN-UAT.md "Bugs surfaced" #2. Don't touch.

The ~2.2x FCP gap suggests the browser is parser-blocked by the monolithic `index-*.js` (69.5 kB gz + ~220 kB raw to parse). The fix targets are:

### What's already optimized (don't redo)

### What changes once vendor-react is correctly split

When `vendor-react-*.js` actually contains react-dom (~50–60 kB gz):
- `index-*.js` shrinks from 69.5 kB gz to ~25–35 kB gz.
- Browser fetches `index` and `vendor-react` **in parallel** (HTTP/2 multiplexing on Vercel — verified, Vercel serves HTTP/2 by default).
- Parser cost drops on the entry path because `index` is smaller.
- React initialization can begin as soon as both arrive (vendor-react is the larger of the two).
- Predicted FCP/LCP improvement: ~600–1200 ms based on the parser-cost reduction. `[ASSUMED — needs Phase 2.1 measurement to confirm]`

### Levers we haven't pulled yet (in priority order)

1. **`<link rel="modulepreload">` for `vendor-react`** — option (b). Already covered above. May be redundant after (a).
2. **`<link rel="preload" as="font">` for the three Google Fonts.** Currently `index.html:13-18` does `preconnect` for `fonts.googleapis.com` + `fonts.gstatic.com` and includes the stylesheet via `<link rel="stylesheet">`. The actual `.woff2` files don't get fetched until the CSS is parsed. Adding `<link rel="preload" as="font" type="font/woff2" crossorigin>` for the actually-used weights of Inter/Fraunces/JetBrains Mono would cut FCP further. **But:** Lighthouse's FCP measurement may not be improved by font-preload because text already uses fallback fonts during the swap window (we use `&display=swap` in the URL — line 16). The bigger LCP impact is likely from the hero element which is a chart/illustration, not text. `[ASSUMED — needs measurement; documented as a Phase 2.2 lever, not 2.1]`
3. **Defer/async on the script.** N/A — `type="module"` already defers per spec.
4. **`<link rel="dns-prefetch">` or `preconnect` for Sentry/PostHog hosts.** Not on first-paint critical path because `vendor-telemetry-*.js` (93 kB gz) is itself in `__vite__mapDeps` — it loads AFTER React mounts. Skip.
5. **Self-host Google Fonts.** Removes the `preconnect` + 2 cross-origin requests on cold load. Real but moderate FCP win. **Out of 2.1 scope** — it's a separate fix and would touch `index.css` + `vercel.json` (CSP `font-src` simplification).
6. **Inline critical CSS.** Vite doesn't do this by default. Would require `vite-plugin-critical` or similar. Aggressive; out of 2.1 scope.

`main.tsx:13-19` calls `Sentry.init()` SYNCHRONOUSLY at module top-level — but the `import * as Sentry from '@sentry/react'` is a static import, which means **the `vendor-telemetry` chunk (93 kB gz) is on the entry's static graph**. ### If (c) is somehow still needed: the canonical reduction path

Three approaches in increasing aggression:

#### C1 — `LazyMotion` + `m` component (smallest change)

`[CITED: motion.dev/docs/react-reduce-bundle-size]` Replace every `import { motion } from 'framer-motion'` with `import * as m from 'motion/react-m'` and wrap the app in `<LazyMotion features={domAnimation}>`.

- Reduces full framer-motion (~34 kB gz isolated, ~113 kB gz with all internals from 02-02 measurement) to ~4.6 kB gz initial render.
- `domAnimation` covers: animations, variants, exit animations, tap/hover/focus gestures, AnimatePresence.
- `domMax` adds: pan/drag gestures and layout animations.
- **Sheet.tsx uses `useDragControls` + `drag="y"`** — that requires `domMax` (per Motion docs). So we'd need `domMax` not `domAnimation` for Sheet.
- Trade-off: cleaner approach, keeps all the API consistency, but requires touching every framer-motion import site (12 files).
- **Risk:** "Including a `motion` component anywhere will break the benefits of using LazyMotion, and a motion component loaded within will throw with a reminder to render the m component instead." `[CITED: motion.dev/docs/react-reduce-bundle-size]` So we need to migrate all 12 imports, not just the critical-path ones. Big touch, low per-file risk.

#### C2 — Replace ornamental usages with CSS, keep framer-motion for Sheet drag

- Replace Sidebar/MobileNav/FocusCard/Toast/UnitToggle motion uses with Tailwind `transition-*` + `motion-safe:` classes.
- Keep framer-motion for: Sheet (drag), Modal (because `AnimatePresence` exit animation cleanly times the unmount), AIChatPanel, OnboardingFlow.
- Reduces framer-motion's per-page footprint but doesn't eliminate the dep.
- Smaller code touch but uneven (some files migrated, some not).

#### C3 — Full swap to motion-one or pure CSS

- motion-one mini = 2.3 kB gz, hybrid = 17 kB gz. `[CITED: reactlibraries.com Framer Motion vs Motion One 2025]`
- BUT motion-one and framer-motion *recently merged* under the "Motion" brand — picking motion-one in 2026 is essentially picking a different facade of the same project. `[CITED: motion.dev/magazine/should-i-use-framer-motion-or-motion-one]`
- Full rewrite is highest risk; not recommended unless we have evidence framer-motion (even with LazyMotion) is too big.

**Recommendation if (c) ships:** start with **C1 (LazyMotion + `m`)**. It's the documented official path, has the smallest API surface change per file, and reaches ~4.6 kB gz which is well within Lighthouse's tolerance. **Do not pursue C2/C3 unless C1 measurably underperforms.**

### Reduced-motion preservation

The codebase honors `prefers-reduced-motion` via `useReducedMotion()` (CLAUDE.md "Accessibility Conventions"). Any CSS-only replacement (option C2) **must wrap animations in `motion-safe:`** Tailwind v4 modifier. `motion-reduce:` for the alternate path. Don't lose this; it's a real accessibility floor.

### P7 — `__vitePreload` polyfill quirks

Vite injects a polyfill for `<link rel="modulepreload">` (Safari < 17 support). When `build.modulePreload.polyfill` is `true` (default), every dynamic import goes through `__vitePreload(...)` which appends a `<link rel="modulepreload">` to the head before fetching. This can cause:
- Duplicate modulepreloads if both the static `<link>` and the dynamic helper try to add the same chunk. Browsers deduplicate, but it's noise.
- A small bytes overhead in every chunk that does dynamic imports.

For 2.1: do NOT disable the polyfill. Safari 16 and earlier are still in the wild. The duplicate-link behavior is harmless. `[CITED: vite.dev/config/build-options "build.modulePreload"]`

### P8 — CSP nonce surprise

If a future change replaces our `script-src 'self'` with `script-src 'nonce-...'`, modulepreload links will need to carry the nonce too (per the Angular CLI #26330 issue). We're not making that change in 2.1, but if anyone does later, the modulepreload `<link>` from option (b) would need a nonce attribute. **Note in the 2.1-BUNDLE-MEASUREMENT.md update for future readers.**

`[CITED: github.com/angular/angular-cli/issues/26330]`

```ts
// inside build.rollupOptions.output
manualChunks(id: string): string | undefined {
  if (id.endsWith('.css')) return undefined;

  if (id.includes('node_modules')) {
    if (/node_modules\/(react|react-dom|scheduler)(\/|$)/.test(id)) {
      return 'vendor-react';
    }
    if (/node_modules\/(framer-motion|motion-dom|motion-utils)(\/|$)/.test(id)) {
      return 'vendor-motion';
    }
    if (/node_modules\/(chart\.js|@kurkle\/color)(\/|$)/.test(id)) {
      return 'vendor-charts';
    }
    if (/node_modules\/lucide-react(\/|$)/.test(id)) {
      return 'vendor-icons';
    }
    if (
      /node_modules\/(@sentry\/react|@sentry\/core|@sentry\/browser|@sentry-internal\/browser-utils|posthog-js)(\/|$)/.test(id)
    ) {
      return 'vendor-telemetry';
    }
  }
  return undefined;
}
```

### Custom modulepreload-emitting Vite plugin (option B1)

```ts
import type { PluginOption } from 'vite';

function emitVendorReactPreload(): PluginOption {
  return {
    name: 'leanshot-emit-vendor-react-preload',
    apply: 'build',
    transformIndexHtml: {
      order: 'post',
      handler(html, ctx) {
        if (!ctx.bundle) return html;
        const chunk = Object.values(ctx.bundle).find(
          (c) => c.type === 'chunk' && c.fileName.startsWith('assets/vendor-react-'),
        );
        if (!chunk) return html;
        const href = `/${chunk.fileName}`;
        if (html.includes(`href="${href}"`)) return html;
        return html.replace('</head>', `    <link rel="modulepreload" href="${href}" />\n  </head>`);
      },
    },
  };
}
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| `splitVendorChunkPlugin()` | `manualChunks` function form | Vite 5 (deprecated), Vite 6 (removed) | The plugin was never robust; function-form manualChunks is the canonical pattern |
| Object-form `manualChunks` | Function-form `manualChunks` | Recommended since at least Vite 4 | Object form has subtle "module already in another chunk" semantics that bite real apps with lazy-loaded routes (this exact bug) |
| `manualChunks` (any form) | `advancedChunks` with groups array | Vite 8 (Rolldown) | Future migration; not in scope for 2.1 but document for 2.x |
| Direct framer-motion imports | LazyMotion + `m` component | framer-motion v6+ | Reduces 34 kB → 4.6 kB initial bundle |

**Deprecated/outdated in our codebase:**
- Object-form `manualChunks` in `vite.config.ts:53-65` — this is what 2.1 replaces.
