Close the four lower-priority but real gap-closure findings — the test-hygiene cluster plus one billing-correctness defect. These do not block the monetization runtime the way CR-01/CR-02/CR-04 do, but they leave Phase 14's verification surface dishonest (a hollow e2e that cannot prove SC#3, a latent runtime-break SDK version split, a SQL test that may error before its assertion) and — in the case of CR-06 — quietly under-bill clinics.

**CR-03 — Stripe SDK version split.** `leanshot/package.json` pins `stripe@^17.7.0` (used by the Node-side bootstrap script + all 3 e2e fixtures), while the Edge Functions import `stripe@19` via `supabase/functions/import_map.json`, and every file hard-codes `apiVersion: '2026-04-22.dahlia'` (a v17 SDK does not type that version or guarantee the request shapes — `stripe-bootstrap.ts` already casts via `as` to suppress the error). Reconcile: pin the npm `stripe` devDependency to `^19.0.0`.

**WR-09 — hollow clinic-metered-billing e2e.** `clinic-metered-billing.spec.ts` calls `stripe.billing.meterEventSummaries.list('mtr_test_placeholder', ...)` with a literal placeholder ID — that call always throws, the test falls into the `catch`, and the cascading fallbacks end with `meterEventFound = webhookResp.status === 200`. The final assertion only throws `if (!meterEventFound && webhookResp.status !== 200)`. Net effect: the test passes on a webhook 200 alone — SC#3 / MONEY-05 ("11 active patients → overage=1") is never actually proven. Fix: read the real meter ID from `process.env.STRIPE_METER_ACTIVE_PATIENTS`, assert `aggregated_value === 1`, remove the status-code escape hatch, and `test.skip` (not pass) when the meter env var is absent.

**CR-05 — invalid enum + column drift in SQL/e2e test data.** `count-active-patients.test.sql:77` (the `v_p3` row) inserts `site = 'abdomen'`, which is not a valid `InjectionSite` value (`src/types/index.ts:27-35`: `abdomen-ul | abdomen-ur | abdomen-ll | abdomen-lr | thigh-l | thigh-r | arm-l | arm-r` — no bare `'abdomen'`). NOTE: line 81 (`v_p5`, the revoked patient) ALREADY uses the valid `'thigh-l'` — only the single `v_p3` literal is wrong. The clinic e2e fixture (`clinic-metered-billing.spec.ts:~141-149`) separately uses `site: 'abdomen'` AND uses `date` + `dose_unit` column names and omits `log_id`, while the live `injections` schema uses `logged_at` + `unit` + a required `log_id` PK component. Fix the one SQL literal to a valid enum value and reconcile the e2e fixture insert to the live schema.

**CR-06 — `count_active_patients()` misplaced `LIMIT 1` (folded in from 14-REVIEW.md).** The billing counter's recent-activity check is a 5-arm `UNION ALL` inside an `EXISTS` subquery (`injections ∪ weights ∪ meals ∪ workouts ∪ symptoms`). The `LIMIT 1` on the final line binds ONLY to the last `UNION ALL` arm (`symptoms`), NOT the whole subquery — so it neither short-circuits the EXISTS nor is harmful by itself, but it makes the query intent dishonest and is a latent footgun for anyone editing the arm order. More importantly, the migration is **not yet pushed to the live DB**, so this is the free moment to also assert (and lock in via the SQL test) that every arm filters on the correct `created_at` column. (Verification confirms: injections, weights, meals, workouts, symptoms ALL have `created_at timestamptz not null default now()` — so the column names are already correct; the only code change needed is removing the misplaced `LIMIT 1`. The SQL test gains a cross-arm fixture row so this stays proven.) Left unfixed, a future arm-reorder or column rename could silently make an arm match zero patients → clinics under-billed.

Purpose: Re-satisfy the MONEY-05 (clinic metered billing — make SC#3 actually provable + the counter correct across all activity types) and MONEY-01 (webhook correctness — consistent SDK) test-confidence portions. Affects SC#3 confidence and clinic billing correctness.
