## Phase Goal

**As a** GLP-1 user (web) or clinic owner, **I want to** have my subscription state authoritatively driven by Stripe webhook events (verified-signed, idempotent, mapped to a UX tier), **so that** my access tier in LeanShot never drifts from what I am actually paying for and dunning recovery is instant.

<objective>
Ship the `stripe-webhook` Supabase Edge Function — the single source of truth for `subscriptions` table state (D-14). This handler:

1. Verifies every event's signature via `stripe.webhooks.constructEventAsync` + `Stripe.createSubtleCryptoProvider()` over the RAW request body (Pitfalls 2 + 3).
2. Deduplicates by `event.id` via `subscription_events` PRIMARY KEY + `INSERT … ON CONFLICT DO NOTHING` (Phase 14 landmine #1, Pattern B).
3. Dispatches to per-event-type handlers in `events/<type>.ts`, each of which collapses Stripe's 8 subscription statuses to the 3-state UX tier (`free` | `paid` | `past_due`) per Pitfall 6.
4. Never echoes Stripe payload content to the response (PII safety).

Purpose: D-14 enforcement. The DB is the audited copy of subscription state; the webhook is the only writer. All downstream Phase 14 frontend gating (`<TierGate>`, `<PastDueBanner>`) reads `subscriptions.ux_tier`. If the webhook is wrong, the entire phase is wrong.

Output: 1 net-new Edge Function (deployed live via `supabase functions deploy stripe-webhook --linked`), 5 event-type handlers in `events/*.ts` (+ 1 stub `invoice-upcoming.ts` reserved for 14-07), 6 Deno test files, 1 line added to `supabase/functions/import_map.json`. Wave 2 parallel with 14-04 (file-disjoint).
</objective>

### Stripe status → ux_tier collapse (Pitfall 6 — canonical)

```typescript
// supabase/functions/stripe-webhook/events/_status.ts (or inline in subscription-updated.ts)
type UxTier = 'free' | 'paid' | 'past_due';
export function mapStripeStatusToUxTier(
  status: Stripe.Subscription.Status,
): UxTier {
  switch (status) {
    case 'trialing':
    case 'active':
      return 'paid';
    case 'past_due':
    case 'unpaid':
      return 'past_due';
    case 'canceled':
    case 'incomplete':
    case 'incomplete_expired':
    case 'paused':
      return 'free';
    default: {
      // Exhaustiveness guard — TS will yell if Stripe adds a new status.
      const _exhaust: never = status;
      return 'free';
    }
  }
}
```

### `subscription_data.metadata` contract (set by stripe-checkout plan 14-04)

```
metadata.provider  = 'stripe'      (always)
metadata.tier_kind = 'web' | 'clinic'
metadata.user_id   = <auth.users.id>   (when tier_kind='web')
metadata.clinic_id = <clinics.id>      (when tier_kind='clinic')
```

The webhook MUST read these fields to know which row of which table to upsert. If `metadata.tier_kind === 'web'` → upsert subscriptions with `user_id = metadata.user_id, clinic_id = NULL`. If `'clinic'` → `clinic_id = metadata.clinic_id, user_id = NULL`. The CHECK constraint enforces exactly-one.

### Response shape — SUCCESS

```
status 200 + body: { "ok": true }
```

### Response shape — FAILURE (NEVER echo Stripe content)

```
status 400 + body: { "error": "bad-signature" }       — sig verify failed (Stripe retries; rotated secret rejects until fixed)
status 400 + body: { "error": "missing-signature" }   — no Stripe-Signature header
status 200 + body: { "duplicate": true }              — event.id already processed (so Stripe stops retrying)
status 500 + body: { "error": "internal" }            — DB or downstream handler error (Stripe retries up to 24h)
```

Stripe's retry policy treats any non-2xx as "retry". `400` and `500` are both retryable from Stripe's side, but `400` means "this request is broken" so Stripe stops retrying after a short window for `400`; `500` triggers the full 24h retry curve. Use `500` for transient DB errors so retries actually help.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Internet → Edge Function | Stripe (or attacker spoofing as Stripe) POSTs a JSON event with a `Stripe-Signature` header. The function MUST verify HMAC before trusting any payload byte. |
| Edge Function → Postgres | Service-role client bypasses RLS — same trust posture as `share` and `clinic-invite`. Writes are confined to 3 tables (`subscription_events`, `subscriptions`, `stripe_customers`/`clinic_stripe_customers`). |
| Postgres → downstream readers | RLS policies from 14-01 ensure only the owning user / clinic admin can SELECT their `subscriptions` row. Service-role-only on `subscription_events`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-03-S1 | Spoofing | POST `/stripe-webhook` from non-Stripe origin | mitigate | Reject with 400 if `Stripe-Signature` header missing OR `constructEventAsync` throws. Verified by Deno test `tampered-body returns 400` (whitespace mutation is the cheapest exploit of body-mutation-before-verify, Pitfall 3). |
| T-14-03-T1 | Tampering | Replay of a previously valid event to flip `ux_tier='paid'` after revoke | mitigate | `subscription_events.event_id PRIMARY KEY` + `INSERT ON CONFLICT DO NOTHING` makes replays no-ops. Verified by Deno test `duplicate event.id returns 200 + does NOT mutate subscriptions`. |
| T-14-03-T2 | Tampering | Body-mutation between Stripe and our handler (proxy injection) | mitigate | HMAC-SHA256 over raw body in `constructEventAsync`. Any whitespace change → signature fails → 400. |
| T-14-03-R1 | Repudiation | "I never received the webhook" claim from downstream debugging | mitigate | Every event (including duplicates that hit the unique violation) is written to `subscription_events` with `received_at`; payload is full Stripe event JSON for forensic replay. |
| T-14-03-I1 | Information Disclosure | Error response echoes Stripe customer email / amount / payment_method | mitigate | All error responses are `{ error: '<short-code>' }`. `console.error` logs the error MESSAGE but never the payload object. Deno test asserts no payload field appears in any response body. |
| T-14-03-I2 | Information Disclosure | Response cached by CDN/proxy and served to attacker | mitigate | `Cache-Control: private, no-store` on every response (including 4xx + 5xx + OPTIONS). |
| T-14-03-D1 | Denial of Service | Attacker floods endpoint with bogus payloads to exhaust DB capacity | accept | Stripe's own rate-limit doesn't apply (attacker is bypassing Stripe). Signature verify on bad payloads is fast (~0.1ms) and returns 400 without DB write. Supabase platform rate-limit at the function level is sufficient for v1.2. Revisit if abuse pattern emerges. |
| T-14-03-E1 | Elevation of Privilege | Service-role key leak via error message or log | mitigate | Standard Phase 5+ posture: SERVICE_ROLE_KEY only read at cold-start into the `admin` constant; never interpolated into responses or thrown errors. Grep gate in verification asserts string `SUPABASE_SERVICE_ROLE_KEY` appears only in the env-read line of index.ts. |
