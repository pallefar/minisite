    2. **The trigger function — verbatim shape from researcher §7 with concrete identifiers:**
       ```sql
       create or replace function public.audit_trigger()
       returns trigger
       language plpgsql
       security definer
       set search_path = public, pg_catalog
       as $$
       declare
         v_before text;
         v_after text;
         v_row_id text;
         v_user_id uuid;
       begin
         -- Resolve the affected user_id from NEW (insert/update) or OLD (delete).
         v_user_id := coalesce(new.user_id, old.user_id);

         -- Hash OLD on UPDATE+DELETE; hash NEW on INSERT+UPDATE.
         -- row_to_json() is sufficient — researcher §7 notes the determinism caveat,
         -- but no consumer compares hashes in v1, so canonicalization is deferred.
         if tg_op = 'UPDATE' or tg_op = 'DELETE' then
           v_before := encode(digest(row_to_json(old)::text, 'sha256'), 'hex');
         end if;
         if tg_op = 'INSERT' or tg_op = 'UPDATE' then
           v_after := encode(digest(row_to_json(new)::text, 'sha256'), 'hex');
         end if;

         -- Composite row_id serialization: works for the 9 composite-PK tables
         -- AND for settings (singleton, PK=user_id).
         v_row_id := coalesce(
           (case when tg_op = 'DELETE' then old else new end)::text,
           ''
         );

         insert into public.audit_logs
           (user_id, user_id_hash, table_name, row_id, action, before_hash, after_hash)
         values (
           v_user_id,
           encode(digest(v_user_id::text, 'sha256'), 'hex'),
           tg_table_name,
           v_row_id,
           lower(tg_op),
           v_before,
           v_after
         );

         return coalesce(new, old);
       end;
       $$;
       ```

       The `set search_path = public, pg_catalog` is the standard SECURITY DEFINER hardening — prevents schema-resolution attacks where a caller injects a schema earlier on `search_path`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Authenticated client ↔ public.audit_logs | JWT-scoped supabase-js client; untrusted input crosses into RLS gate. |
| Sync table trigger ↔ public.audit_logs | SECURITY DEFINER function inside Postgres; trusted, runs as function owner (Supabase `postgres` role — non-superuser on managed platform). |
| pg_cron job ↔ public.audit_logs | Server-internal scheduled DELETE; runs as cron-owner role; not user-reachable. |
| Service-role edge function ↔ public.audit_logs | Will arrive in plan 07-07 (account-delete RPC writes skeleton rows); bypasses RLS by design. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-08-01 | **Tampering** | authenticated role direct write to audit_logs | mitigate | NO INSERT/UPDATE/DELETE policy exists for authenticated role on audit_logs. Migration A documents the intentional omission. Only the SECURITY DEFINER `audit_trigger()` function (which runs as function owner) and the service_role can write. Task 5 Test 4 + Task 6 Test 2 prove the deny at runtime. |
| T-07-08-02 | **Tampering** | SECURITY DEFINER function search_path hijack | mitigate | Function declares `set search_path = public, pg_catalog`. Prevents an attacker from creating a `digest()` shim in a schema earlier on the caller's search_path. |
| T-07-08-03 | **Repudiation** | "I never deleted my account" / "I never logged that injection" | mitigate | audit_logs row is written in the same transaction as the underlying write (AFTER trigger). Skeleton subset (action LIKE 'account_deleted_%') is EXCLUDED from the 13-month retention cron — survives forever. user_id_hash (sha256) is `not null` so attribution survives even after `auth.users` row is cascade-deleted (FK is `on delete set null` on user_id, preserving the row). |
| T-07-08-04 | **Information disclosure** | User A reads user B's audit history | mitigate | RLS `audit_logs_select_own` policy: `using (auth.uid() = user_id)`. Cross-tenant proof in `e2e/rls-audit-logs.test.ts` (Task 6 Test 1) — user B's SELECT returns `[]`. This is the project-rule-mandated live impersonation proof. |
| T-07-08-05 | **Information disclosure** | Hashed PII reverse-lookup (rainbow attack on user_id_hash) | accept | uuid is 128 bits of entropy → 2^128 search space. Sha256 brute-force infeasible. user_id_hash is not "personal data" once the source `auth.users` row is gone (key justification for why the skeleton subset is GDPR/WMHMDA-compatible per CONTEXT D-03). |
| T-07-08-06 | **Denial of service** | Unbounded audit_logs growth fills DB quota | mitigate | Nightly pg_cron `cleanup-audit-logs` job at 05:00 UTC: `DELETE WHERE timestamp < now() - interval '13 months' AND action NOT LIKE 'account_deleted_%'`. Skeleton retained indefinitely; full per-write log rolls off at 13mo. |
| T-07-08-07 | **Denial of service** | Trigger overhead on hot write path (every injection insert pays a sha256 cost) | accept | sha256 of a small JSON row is sub-millisecond on managed Postgres. Insert latency budget already absorbs this. If a future profile shows trigger overhead >5% of write latency, revisit with a hash-on-write-coalesce optimization. Recorded in deferred ideas. |
| T-07-08-08 | **Elevation of privilege** | SECURITY DEFINER function executing with elevated permissions | mitigate | Function owner is the Supabase `postgres` role — NOT a superuser on managed Supabase (the platform restricts it). The function ONLY performs a single INSERT into a table the owner controls; no dynamic SQL, no `execute` of user input, no role-switching. `set search_path` hardened (T-07-08-02). |
| T-07-08-09 | **Elevation of privilege** | Attacker registers a shadow `digest()` in `public` to bypass hashing | mitigate | `set search_path = public, pg_catalog` resolves `digest` from `public` first if shadowed, BUT `digest` is in the `pgcrypto` extension (default-installed into the `extensions` schema OR `public`, depending on Supabase project config). Migration A `create extension if not exists pgcrypto` ensures the function exists; the search_path hardening + the fact that authenticated callers cannot CREATE objects in `public` (default Supabase grants) closes the gap. |
