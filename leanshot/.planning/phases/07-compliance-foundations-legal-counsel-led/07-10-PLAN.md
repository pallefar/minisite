<objective>
**As a** patient whose pre-cloud-migration data was clobbered by a bad sync,
**I want to** restore the 90-day local backup snapshot from a Settings → Recovery panel,
**so that** I can roll back to a known-good local state without contacting support — provided I confirm explicitly enough that an accidental click cannot do the damage.

Purpose: Closes D-05 — the Phase 6 cliffhanger. Phase 6 D-03 wrote `leanshot_v4_pre_cloud_backup` to localStorage with shape `{state, version: 7, snapshotAt: ISO}` before any cloud write, but punted the user-facing restore UI to Phase 7. This plan ships the consume-side: a Recovery panel in Settings that reads the backup, shows its date, gates the destructive action behind a typed-confirmation, and post-restore signs the user out so the next sign-in resolves LWW deterministically against the restored local rows.

Output:
- New "Recovery" nav entry + Section in `SettingsPage.tsx` (sibling to existing Privacy + Data sections)
- Backup-presence detection: read `localStorage['leanshot_v4_pre_cloud_backup']` once when Settings opens; hide the section when absent OR render empty-state copy
- Snapshot date display parsed from `backup.snapshotAt`
- Typed-confirmation modal (user types `RESTORE` to enable the destructive button) + explicit warning copy
- Restore action: `useStore.setState(backup.state, true)` (replace mode, partialized shape) + `signOut()` from `@/lib/auth` to force re-sync on next sign-in
- Graceful error toast on malformed JSON (try/catch around `JSON.parse`)
- Unit tests: `SettingsPage.test.tsx` — confirmation gating + setState invocation + sign-out invocation + malformed-JSON path
- E2E: `e2e/restore-from-backup.spec.ts` — seed backup → click Restore → type `RESTORE` → assert state replaced + sign-out occurred
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User device localStorage → application memory | A user-controlled artifact (`leanshot_v4_pre_cloud_backup`) is read and used to replace in-memory app state. Local-storage tampering is implicitly accepted as in-scope-for-local-attacker only (per RESEARCH §8 threat table) — this plan does not introduce a cloud-side attack surface. |
| Settings UI → Zustand store | A destructive action (full state replace) crosses the user-interaction boundary. Mitigation = typed confirmation + sign-out post-restore to prevent stale-server-state desync. |
| Restored state → Supabase realtime backend | After restore, the local state and server state diverge. LWW guarantees eventual consistency; sign-out forces a clean re-pull on next sign-in instead of an immediate race. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-10-01 | Tampering / Integrity | `SettingsPage.tsx` Restore button → `useStore.setState(backup.state, true)` | mitigate | Typed-confirmation gate: destructive confirm button is `disabled` until the user types the literal case-sensitive string `RESTORE`. Single click on the Restore button is non-destructive (only opens the modal). |
| T-07-10-02 | Tampering / Integrity | `useStore.setState` invoked with parsed backup JSON | mitigate | Pass `replace=true` (Zustand setState second arg) so ONLY the partialized shape is applied. `currentTab`, `toast`, and `signedIn` are not in the backup (Phase 6 D-03 wrote partialized shape) so they cannot be replayed into a privileged state. The typed-cast `as Parameters<typeof useStore.setState>[0]` is a structural compile-time check, not a runtime trust boundary — the runtime authority for what is restored is the partialize allow-list itself (`src/lib/store.ts:1865`). |
| T-07-10-03 | Tampering / Information Disclosure | Post-restore Supabase realtime subscriptions hold a stale session against the restored local rows | mitigate | `await signOut()` is called AFTER `setState` but BEFORE the user can interact with the dashboard. Closing the Settings modal at the end completes the boundary transition. On next sign-in, Realtime subscriptions re-bind with fresh server state against the restored local snapshot, and Phase 5 D-08 LWW resolves divergences deterministically. |
| T-07-10-04 | Denial of Service / Integrity | Malformed backup JSON (corruption, partial write, hostile edit) crashes the Settings UI on read | mitigate | Both `localStorage.getItem` and `JSON.parse` are wrapped in `try/catch`. | T-07-10-05 | Elevation of Privilege | Hostile-crafted backup JSON injects claims (admin flag, fake user_id) into the restored state | mitigate (boundary-shifted) | The Zustand store does NOT hold auth/authorization claims — those live in the Supabase JWT controlled by `auth.users` row + RLS. Even if `state.user.id` is crafted to a different UUID, all server reads/writes are filtered by `auth.uid()` on the SERVER (Phase 5 D-09 RLS).
