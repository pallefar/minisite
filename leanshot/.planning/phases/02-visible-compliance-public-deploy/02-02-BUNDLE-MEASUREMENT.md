## Largest passengers in the main chunk (ranked)

1. **framer-motion** ≈ 113 kB gzipped (per-module) — single largest passenger; ubiquitous in UI.
2. **react-dom** ≈ 98 kB gzipped (per-module) — non-removable.
3. **@sentry/core + @sentry/browser + @sentry-internal/browser-utils** ≈ 116 kB gzipped (per-module sum) — Wave-3 instrumentation; can move to its own chunk.
4. **posthog-js** ≈ 61 kB gzipped (per-module) — Wave-3 analytics; can move to its own chunk.
5. **lucide-react** ≈ 8 kB gzipped (per-module) — already tree-shaken; small enough to leave or split for cache stability.
6. **chart.js** ≈ 103 kB gzipped (in BaseChart, NOT index) — already lazy; splitting it into `vendor-charts` keeps the BaseChart wrapper small and the chart.js chunk shareable across all chart-using tabs (Body/Home/Insights/Medication).

## Proposed manualChunks for 02-07

Based on the measurements above, the planner's recommended grouping is:

```js
// vite.config.ts -> build.rollupOptions.output.manualChunks
manualChunks: {
  'vendor-react': ['react', 'react-dom', 'scheduler'],     // ~107 kB gz pre-bundle, ~50–60 kB gz emitted (cache-friendly, rarely changes)
  'vendor-motion': ['framer-motion', 'motion-dom', 'motion-utils'], // ~120 kB gz pre-bundle (largest passenger; pulled out of first paint)
  'vendor-charts': ['chart.js', '@kurkle/color'],          // ~108 kB gz pre-bundle (already lazy; just isolated for cache-stability)
  'vendor-icons': ['lucide-react'],                         // ~8 kB gz (small but cache-stable; isolating keeps icon-only updates from invalidating index)
  'vendor-telemetry': ['@sentry/react', '@sentry/core', '@sentry/browser', '@sentry-internal/browser-utils', 'posthog-js'], // ~178 kB gz pre-bundle — splits ALL Wave-3 telemetry into one async chunk
}
```

Together, vendor-react + vendor-motion + vendor-telemetry cover **97 kB + 113 kB + 178 kB ≈ 388 kB / 434 kB ≈ 89%** of the index chunk's pre-bundle gzipped mass — well above the 60% threshold. After splitting, `index-*.js` should drop to roughly 20–30 kB gzipped (just src/* + zustand + a sliver of glue), and the four vendor chunks load in parallel.

> **Decision input for human checkpoint (Task 3):**
>
> 1. Should `vendor-telemetry` be split further (e.g., separate `vendor-sentry` and `vendor-posthog`) so PostHog can be lazy-loaded behind a consent gate while Sentry stays eager? This depends on whether 02-06 ships a consent toggle for analytics-only.
> 2. Should `vendor-charts` stay merged into `BaseChart` (current state) or be promoted to its own vendor chunk? The proposal above promotes it for cache-stability (chart.js rarely changes; LeanShot src changes often).
> 3. Should `lucide-react` stay merged with src (`index`) for tree-shaking efficiency, or split out for cache-stability? At 8 kB gz it is small either way.

## Lighthouse 90 floor — confidence

**Rating: HIGH.**

Rationale:
- The largest five passenger groupings (framer-motion, react-dom, sentry, posthog, chart.js) account for **89% of the per-module gzipped mass** in the always-loaded `index` chunk and the lazy `BaseChart` chunk. Splitting them exceeds the 60% target stated in the planner heuristic (D-23).
- After the split, the critical path on a cold load drops from ~206 kB gz (single index) + parser cost, to ~20–30 kB gz (slim index) + four parallel vendor chunks the browser can fetch concurrently while React boots — the Lighthouse-relevant **First Contentful Paint** and **Largest Contentful Paint** metrics will both benefit since `react-dom` and `framer-motion` will land in parallel rather than serially after parsing the monolithic index.
- `BaseChart` (71.5 kB gz emitted) is already lazy — Home/Body/Medication tabs are NOT on the critical first-paint path (`Landing` is). The marketing landing (`Landing-l7glf1nC.js`, 5.9 kB gz) is the only first-paint feature module on top of the slim `index`.
- Risk mitigations:
  - If 02-07 reveals that the proposed grouping over-fragments (e.g., HTTP/2 head-of-line blocking on too many small chunks), the fallback per D-25 is to merge `vendor-icons` back into `index` and keep `vendor-react` + `vendor-motion` + `vendor-telemetry` + `vendor-charts` as the four vendor groupings. This still exceeds 60%.
  - If Lighthouse still fails ≥ 90, the next lever (per D-25) is preloading `vendor-react` via `<link rel="modulepreload">` in `index.html`, which is a single-line change after measurement.

**Flag for 02-08:** Measure Lighthouse in 02-08 against both the bare landing route AND the dashboard-after-onboarding route. The dashboard-route Lighthouse score depends on whether `vendor-charts` is fetched eagerly (current: lazy via Suspense — keep that).

## Reproduction

```bash
cd leanshot
ANALYZE=true npm run build       # produces dist/stats.html
open dist/stats.html              # macOS — opens treemap in default browser

# Per-chunk emitted gzipped sizes
for f in dist/assets/*.js; do
  raw=$(wc -c < "$f")
  gz=$(gzip -c "$f" | wc -c)
  printf "%s  raw=%s gz=%s\n" "$(basename "$f")" "$raw" "$gz"
done | sort -t= -k3 -n -r | head
```

The visualizer JSON inside `dist/stats.html` (search for `const data = `) carries the per-module gzip/brotli numbers used in the "Inside `index-*.js`" table above.
