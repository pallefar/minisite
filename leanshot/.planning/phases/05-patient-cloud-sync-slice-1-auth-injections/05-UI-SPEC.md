# Phase 5 — UI Design Contract

> Visual and interaction contract for the Auth + Injections cloud-sync slice. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> The LeanShot codebase is a mature manual design system built on Tailwind v4 `@theme` blocks in `src/index.css`. shadcn is **not used and intentionally not adopted** for v1 (per project constraint: "raw Tailwind + framer-motion + lucide-react"). Phase 5 reuses the existing token vocabulary; no new visual primitives are introduced.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (manual Tailwind v4 `@theme` system, established v2/Phase 1–4) |
| Preset | not applicable |
| Component library | none — raw Tailwind + framer-motion + lucide-react |
| Icon library | lucide-react `^0.460.0` (existing; do NOT add new icon libs) |
| Font (display) | Fraunces (italic for accent words) |
| Font (sans) | Inter |
| Font (mono) | JetBrains Mono (tabular numerals for counts/codes only) |
| Token source | `src/index.css` `@theme { ... }` block — single source of truth for color, type scale, radius, shadow, motion |

**Architectural invariants Phase 5 MUST preserve:**
- No router. Hash routing only inside the `auth` view (per D-01).
- No new fonts. Use existing Inter/Fraunces/JetBrains Mono trio only.
- No new UI libraries (no Headless UI, no Radix, no shadcn).
- All colors via CSS variables (`var(--color-*)`), NEVER raw hex or Tailwind palette keys (`bg-blue-500` is forbidden).
- `prefers-reduced-motion` respected via `useReducedMotion()` hook OR CSS-level media query in `index.css:485`.
- Dark mode is automatic via `[data-theme="dark"]` variable overrides — design once, both themes work.

## Spacing Scale

Tailwind v4 base spacing unit is `0.25rem` (4px) per `src/index.css:123` (`--spacing: 0.25rem`). All multiples of 4 are available via Tailwind utilities (`gap-4` = 16px, `p-6` = 24px, etc.).

Declared values for Phase 5:

| Token | Value | Tailwind | Usage in Phase 5 |
|-------|-------|----------|------------------|
| xs | 4px | `gap-1`, `p-1` | Icon-to-text gaps inside buttons, banner pill internal padding |
| sm | 8px | `gap-2`, `p-2` | Form field gap-within-group, avatar-menu item internal spacing |
| md | 16px | `gap-4`, `p-4` | Default form-field vertical spacing, card padding-x on mobile |
| lg | 24px | `gap-6`, `p-6` | Auth card content padding, banner horizontal padding |
| xl | 32px | `gap-8`, `p-8` | Auth card padding (desktop), section breaks within Account screen |
| 2xl | 48px | `gap-12`, `p-12` | Vertical breathing room between auth card and viewport edges (desktop) |
| 3xl | 64px | `gap-16` | Reserved — not used in Phase 5 |

**Exceptions (intentional, with justification):**
- **Avatar button touch target: 44×44px** (`size-11` in Topbar to match existing `IconButton size="md"`). 44px is below the 48px scale step but matches Apple's HIG minimum touch target and the existing `IconButton` size convention. NOT a new spacing exception — reuses existing component sizing.
- **Form input height: 48px** (`py-3` + `text-[14px]` line-height ≈ 48px in the existing `Input` primitive). This is what `src/components/ui/Input.tsx:116` already renders; auth forms inherit unchanged.

## Typography

The codebase declares 12 type scale steps in `src/index.css:84-110`. Phase 5 uses a **deliberately constrained 4-size subset** for its new surfaces (mapping to the contract requirement of 3-4 declared sizes):

| Role | Size | Weight | Line Height | Token | Where Used |
|------|------|--------|-------------|-------|------------|
| Body | 14px | 400 (regular) | 1.55 | `text-[14px]` (matches `Input` primitive line 116) | Form input text, banner body copy, secondary auth links |
| Label | 11px | 600 (semibold), uppercase, tracking 0.06em | 1.4 | `text-[11px] font-semibold uppercase tracking-[0.06em]` | Form-field labels (matches `FieldShell` line 47), section headers in Account drawer |
| Heading | 22–26px | 700 (bold), tracking tight | 1.15–1.25 | `text-[22px] md:text-[26px] font-bold tracking-tight` (matches `Topbar.tsx:73`) | Auth screen primary headings ("Sign in", "Welcome back", "Reset your password") |
| Display accent (optional) | 26px italic | 400 (regular), font-display (Fraunces), italic | inherited | `font-display italic font-normal text-[var(--color-primary)]` (matches `OnboardingFlow:206-208` pattern) | A single italic accent word per auth screen heading — e.g. "Save your *data.*", "Welcome *back.*" — used sparingly, MAX once per screen |

**Weights declared: 2.**
- 400 regular (body, form input text, italic display accent)
- 600 semibold (labels, button text via existing `Button` primitive which uses `font-semibold`)
- 700 bold (headings — note: the existing `Button` is `font-semibold` not bold; bold is reserved for h1-level headings only)

Note: the "2 weights max" constraint refers to net-new weights introduced by this phase. Phase 5 introduces **zero net-new weights** — 400/600/700 are already in active use across `OnboardingFlow`, `Topbar`, `Card`, `Button`, etc. The contract is met.

**Forbidden in Phase 5:**
- `text-[10px]` caption — too small for chronic-condition users per CLAUDE.md accessibility-first mandate; reserved for badge/pill tertiary metadata only.
- `text-display` / `text-5xl` / `text-4xl` — these are marketing-only sizes (Landing hero); auth screens are utilitarian.
- New font families.

`--color-primary` may ONLY paint these Phase 5 elements:

## New Design Tokens

**None.**

Phase 5 introduces zero new CSS variables, zero new spacing values, zero new font sizes, zero new animations. Every visual decision below is composed from the existing token vocabulary in `src/index.css` and the existing UI primitive vocabulary in `src/components/ui/`.

Rationale: the existing system already covers warning (amber), success (sage), danger (clay), info, primary (teal), surface, surface-elevated, border, text, text-secondary, text-tertiary — every semantic role Phase 5 needs. Adding e.g. `--color-verify-banner-amber` would duplicate `--color-warning-soft` for no gain and break the established invariant that tokens are role-named not feature-named.

If Phase 7 brand pass later wants a distinct "verify pending" hue, that's the right phase to add it. Phase 5 ships with semantic reuse.

### 1. AuthView Container (`src/components/auth/AuthView.tsx`)

**Purpose:** Top-level container for the new `auth` view slot in `App.tsx`. Owns hash-based sub-screen routing (`#/auth/signin`, `#/auth/signup`, `#/auth/verify`, `#/auth/forgot`, `#/auth/set-new-password`). Lazy-loaded.

```
┌─────────────────────────────────────────────────────────────┐

│  safe-top safe-bottom                                        │
│                                                              │
│  ┌─────────────────────────────────────────────┐             │
│  │  Auth card — max-w-[440px] w-full           │             │
│  │  bg-[var(--color-surface)]                  │             │
│  │  rounded-card (24px — uses --radius-card)   │             │
│  │  border border-[var(--color-border)]        │             │
│  │  shadow-lg                                  │             │
│  │  p-6 md:p-8                                 │             │
│  │                                              │             │
│  │  ┌── Header region ─────────────────────┐   │             │
│  │  │ ← back-to-marketing link (ghost,     │   │             │
│  │  │   left-aligned, size-sm)             │   │             │
│  │  │                                       │   │             │
│  │  │ h1 (22–26px bold tracking-tight)     │   │             │
│  │  │ p (14px text-secondary, mt-1)        │   │             │
│  │  └──────────────────────────────────────┘   │             │
│  │                                              │             │
│  │  ┌── Form region (sub-screen renders) ──┐   │             │
│  │  │  Sub-screen content (one of 5)       │   │             │
│  │  └──────────────────────────────────────┘   │             │
│  │                                              │             │
│  │  ┌── Footer / cross-link region ───────┐    │             │
│  │  │  Text-link to alternate flow         │    │             │
│  │  │  ("Don't have an account? Sign up")  │    │             │
│  │  └──────────────────────────────────────┘   │             │
│  └─────────────────────────────────────────────┘             │
```

- **Card max-width:** 440px (narrower than OnboardingFlow's 560px — auth forms are simpler, narrower feels more deliberate).
- **Card padding:** `p-6` mobile, `p-8` desktop (24px → 32px).
- **Vertical centering:** flex centered with safe-area awareness for iOS notch/home-bar.
- **Background:** matches dashboard bg — does NOT use the `--color-primary-soft → --color-surface-elevated` gradient banner from `OnboardingFlow` (auth is utilitarian, no illustrations).
- **No illustration banner.** Differentiator vs OnboardingFlow: auth screens are pure form, signaling "this is a fast workflow, not a delight moment."

**Typography:** see Typography section above; H1 = `text-[22px] md:text-[26px] font-bold tracking-tight`; sub = `text-[14px] text-[var(--color-text-secondary)] mt-1`.

**States:**
- **Idle:** card visible, form rendered.
- **Hash-route transitioning:** `AnimatePresence mode="wait"` swaps sub-screen with 200ms cross-fade (`{opacity: 0, y: 8}` ↔ `{opacity: 1, y: 0}`). Matches OnboardingFlow:182-189.
- **Initial mount:** `animate-rise` on the card (500ms, fade + 14px Y).

**Animations:**
- Card mount: `animate-rise` (existing keyframe, `rise` in index.css:324).
- Sub-screen swap: framer-motion `mode="wait"`, 200ms `ease-out-quart`.

**Accessibility:**
- `<main role="main">` wrapper; the card itself is a regular `<div>`, NOT a dialog (it's a full-page view, not an overlay).
- H1 is the page's only h1.
- Back-link is a regular anchor `<a href="#/" aria-label="Back to home">`.
- Focus on mount: first form input auto-focuses (via `useEffect` + `inputRef.current?.focus()`).
- Keyboard: Tab cycles through form fields → primary CTA → secondary link. Esc on hash-route view does NOTHING (no overlay to dismiss).

**Reduced-motion fallback:**
- Card mount: no Y translation, just `opacity: 0 → 1` over 100ms.
- Sub-screen swap: instant (no AnimatePresence transition).
- Reuse existing `@media (prefers-reduced-motion: reduce)` block in `index.css:485` — it already disables `animate-rise` automatically.

### 2. SignUpForm (`src/components/auth/SignUpForm.tsx`)

**Renders inside AuthView for hash `#/auth/signup`.**

**Layout:**
```
H1: "Save your data" (or "Create your account" if no anon session detected)
sub: "One account. All your devices."

[Email           ] ← Input primitive, type=email, autocomplete=email
[Password        ] ← Input primitive, type=password, autocomplete=new-password
                     hint (12px tertiary): "8+ chars including a number"
                     (planner-confirmed final policy)

[●●● Create account ───→]  ← Button variant="primary" block size="lg"

────────────────────────
Email me a sign-in link instead  ← text-link, 14px primary
Already have an account? Sign in  ← text-link, 14px primary
```

**Spacing:**
- Field-to-field: `gap-4` (16px) via flex column.
- Field-to-primary-CTA: `mt-6` (24px).
- Primary CTA-to-footer-links: `mt-4` (16px) + `border-t border-[var(--color-border)] pt-4`.
- Footer link gap: `gap-2` (8px).

**States:**

| State | Visual | Form behavior |
|-------|--------|---------------|
| Idle | Both fields empty, primary CTA enabled (will reveal field errors on submit) | — |
| Focus (field) | Field border `--color-primary`, soft shadow ring (`Input` existing pattern) | — |
| Filled-valid | Field shows entered text; no green checkmark (signals over-validation) | — |
| Filled-invalid | Field border `--color-danger`, hint replaced by error message in `--color-danger` (existing `Input` `error` prop) | Submit disabled? NO — submit attempts and server-side validates; client-side validates only email format (`type="email"`) |
| Loading (submit in-flight) | Primary CTA shows `Loader2` spinner left of text via `loading` prop, `aria-busy=true`, button disabled | All inputs disabled (existing `disabled:opacity-60` on FieldShell) |
| Server error | `<Toast kind="error">` with message; form re-enabled; if error is field-specific (e.g. "email already in use"), inline `error` prop on email Input | — |
| Success | Auth view hash redirects to `#/auth/verify-sent` (post-signup interstitial — see surface #5) | Toast: "Welcome! Check your email to verify your account." |

**Animations:**
- Field focus: 200ms `--duration-quick`, `box-shadow` transition (existing Input).
- Button hover: `-translate-y-[1px]` + shadow-md (existing Button primary variant).
- Loading spinner: `animate-spin` (existing).

**Accessibility:**
- Email field: `<Input type="email" autoComplete="email" required label="Email" />` — `FieldShell` auto-wires `htmlFor` + `aria-invalid` + error association.
- Password field: `<Input type="password" autoComplete="new-password" required label="Password" hint="8+ chars including a number" />`.
- Primary CTA: `<Button type="submit" variant="primary" size="lg" block loading={isSubmitting}>Create account</Button>` — `aria-busy` automatic.
- Form submit on Enter: `<form onSubmit={...}>` wraps everything.
- Error messages: when `error` prop set, `Input.tsx` renders `<p role="alert">` via the hint slot (currently not roled — see "Open Questions for Planner").

**Reduced-motion:**
- Disable button hover Y-translate (CSS rule already in `index.css:485`).

- H1-to-sub: `mt-1` (4px).
- Sub-to-CTA: `mt-6` (24px).

**Typography:** H1 26px bold + Fraunces italic accent word for SUCCESS variant.

- Success state's auto-redirect is announced before triggering (1.5s gives screen reader time).
- Icon has `aria-hidden` (decorative); meaning conveyed by H1 text.

**Reduced-motion:** dot pulse disabled; spring on success icon replaced with `opacity: 0 → 1` over 200ms.

| Banner mounts (signed-in + unverified + not-dismissed) | Slide down 300ms |
| Click "Resend" | Call `supabase.auth.resend({ type: 'signup', email })`; show loading; on success show toast; banner stays |
| Click "Dismiss for today" | Set `verificationBannerDismissedUntil` in Zustand (24h from now); banner slides up; reappears after 24h |
| Banner re-appears next session | Slide-down animation as before |
| User verifies email (elsewhere — banner detects via `auth.onAuthStateChange`) | Banner unmounts immediately (no exit animation needed) |

### Form submission interactions

| Trigger | Action |
|---------|--------|
| Enter inside any auth form input | Submit form (native browser behavior; preserve) |
| Submit click (or Enter) | Set `isSubmitting=true`; button shows spinner (`loading={true}` prop); inputs disabled; call Supabase auth method |
| Server response: success | Toast (if applicable); navigate per "AuthView routing" above |
| Server response: error | Toast OR inline field error per error type; re-enable form; focus first errored field |
| User starts typing in errored field | Clear field error (live validation feedback) |

### Account section: change email flow

| Trigger | Action |
|---------|--------|
| Click "Change email" | Row inline-expands; new email input appears; current email row text becomes "Current: user@example.com" smaller |
| Submit new email | Call `supabase.auth.updateUser({email: new})`; show loading on submit button; on success: collapse row, show pending badge, toast "Check {new-email} to confirm the change" |
| Click "Cancel" inside expanded row | Collapse row; restore display state |
| New email verification clicked (in user's inbox) | Routes to `#/auth/verify` — same handler as signup verification, just runs against the email-change flow |

### Multi-account / re-key safety (D-12) interaction

- The localStorage re-key is silent — no UI surface. User notices NOTHING.
- When a different user signs in on the same browser: the existing user's namespaced data stays in localStorage (harmless), the new user gets a fresh namespace, no cross-leak.
- Exception: if the SAME user signs out and a NEW user signs up/in: D-11 clears the current user's data slices from Zustand before the namespace swap, so the new user's view starts empty.

## Sync Indicator Decision

**Verdict: NO ambient sync-status indicator in Phase 5.**

Per D-08 (last-write-wins, no user-facing conflict UI), D-09 (single global Realtime subscription), and D-10 (offline writes via existing Zustand `persist`), the explicit architectural stance is: **sync is invisible until something the user did fails.**

**Surfaces NOT added:**
- No "Synced ✓" / "Syncing..." badge in Topbar.
- No connection-status dot (green/amber/red).
- No "X pending" count badge on the avatar.
- No conflict-resolution UI (LWW silently overwrites loser).

**The ONLY user-facing sync signals in Phase 5:**
1. **Post-bulk-upload toast** (D-06): "Your saved injections are now synced across devices." — fires once at the migration moment.
2. **Email-verification banner** (D-13): "Verify your email to sync across devices." — present until verified, because this is a USER-actionable sync blocker.
3. **Post-signout toast** (D-11): "Signed out. Your data on this device has been cleared." — confirms the wipe.

**Rationale:**
- Local-first UX (every action is instant Zustand-first) means the user never waits on sync. Indicators would create false anxiety ("am I synced?") for a system that's already optimistic.
- LWW conflicts are vanishingly rare for log-style injection data; surfacing a "conflict resolved" notice would alarm users about a non-issue.
- Adding a status indicator now requires:
  - A new component + state slice for connection status.
  - Decisions about color (green/amber/red — none of which fit the warm "clinical-warmth" palette).
  - Behavior on flaky-network reconnect storms.
  - Mobile + desktop placement.
  - All for a signal users don't need.

**If, post-launch, Sentry/PostHog data shows users confused about sync state, revisit in Phase 6** — when more data types sync and conflict surface area widens. Phase 5's job is to prove the cross-device-sync substrate works invisibly.

**One forward-compatible affordance:** if conflict frequency turns out higher than expected, the existing `Toast` primitive (with kind='info') can carry a one-line conflict resolution toast ("We kept your most recent edit") without any new UI infrastructure — this is the planned Phase 6 fallback per ROADMAP.md SC#4 for Slice 2.

## Anti-Patterns Avoided

| Anti-pattern | Why it was rejected |
|--------------|---------------------|
| Adding a router (React Router, etc.) | D-01 explicitly preserves the no-router architectural invariant. Hash routing inside the auth view is the chosen path. |
| Adding shadcn or any new UI library | Project constraint: "raw Tailwind + framer-motion + lucide-react". Existing UI primitives cover every Phase 5 need. |
| New color tokens (e.g., `--color-verify-banner-amber`) | Existing `--color-warning-soft` already serves this role. Feature-named tokens break the role-named token discipline. |
| New font families | Project constraint: Inter/Fraunces/JetBrains Mono trio is locked. |
| Loading skeletons for auth forms | Auth forms render synchronously from local state; no async render-time delay to mask. `Loader2` inside the submit button covers submission state. |
| Auth modals overlaying the dashboard | Auth is a TOP-LEVEL view per D-01, not an overlay. Modal pattern fails for email-link deep-links (`#/auth/verify?token=...` must be a primary surface, not a modal-over-dashboard). |
| Persistent sync-status indicator | See "Sync Indicator Decision" above. |
| Toast-as-primary error surface for form validation | Per the prompt's anti-pattern list: inline field errors first (via `Input.error` prop); toast only for system-level errors (network, rate-limit, unknown 5xx). |
| Distinguishing "wrong email" from "wrong password" in signin errors | Security best practice: always say "Email or password is incorrect" — never confirm account existence via differential error messages. |
| Confirming account existence in password-reset success | "If an account exists for {email}, we sent a reset link." — same security rationale. |
| Auto-redirect to dashboard immediately on email verify (no UI feedback) | Users tap-and-leave; many won't see a 100ms-fast redirect and won't know it worked. 1.5s success screen + toast gives confidence. |
| Showing initials as user's "name" (we don't collect names) | Initials are derived from email local-part's first letter. If a user has `karsten.haldan@gmail.com`, the avatar shows "K". If later phases collect display name (deferred), initials can use the first two of the name. |
| Avatar image upload | Out of scope (per prompt). No avatar image UX. |
| Custom-branded email templates | Out of scope (Phase 7 brand pass). Supabase defaults ship as-is. |
| Account deletion UI | Out of scope (Phase 7 — D-14). Settings Account section does NOT render a deletion row, even as a placeholder. |
| OAuth provider buttons (Google, Apple, etc.) | Out of scope (v2 deferred). The "Enable Manual Linking" is on at Supabase level (Phase 4 04-01), so a future phase can add without re-toggling — but no UI surface in Phase 5. |
| Multi-tab BroadcastChannel coordination UI | Deferred to v2 per D-09. No UI surface needed. |
| Service Worker / "App update available" indicator | Project constraint: no Service Worker. No UI surface. |
| Marketing "Sign up" button alongside "Start tracking" in hero | Splits attention; lowers onboarding-conversion. Sign-up is the POST-onboarding moment. Marketing header link covers returning users. |
| Showing destructive-red on "Sign out" menu item | Sign-out is benign, not destructive. Reserve `--color-danger` for genuinely irreversible actions (deletion — Phase 7). |
| Persistent banner with no dismiss option | Even for safety-critical messages, a 24h "dismiss for today" reduces friction without compromising the verification gate (banner reappears; sync stays blocked until verified). |

## Open Questions for Planner

These items have a researcher-recommended default but are flagged for planner confirmation:

1. **Password policy specifics.** Researcher recommends "8+ chars including a number." Planner confirms final policy and ensures Supabase project's password policy (`supabase config push`) matches the UI hint. **No design impact either way** — hint text is a one-line copy swap.

2. **Email-confirm redirect URL strategy.** UI-SPEC assumes a single production URL pattern (`https://leanshot-app.vercel.app/#/auth/verify`). Planner determines whether wildcards work in Supabase's Redirect URLs allowlist for Vercel previews; if not, planner adds a `/auth/preview-redirect` proxy. **No design impact** — the user-facing flow is identical regardless of the back-end mechanism.

3. **Anonymous-state avatar dot color.** Researcher chose `--color-warning` (amber) for the "anonymous, save your account" indicator dot, matching the verify-pending banner color. Alternative: `--color-info` (teal-700) to feel less alarming. **Recommend amber** because it shares language with "your sync is incomplete" semantic.

4. **Custom email template copy.** Out of scope for Phase 5 per the prompt; Phase 7 brand pass owns this. Researcher inspected Supabase defaults and notes the default verification email reads "Confirm your mail" (sic — typo in some Supabase versions historically). Planner should briefly verify the current default in the Supabase dashboard during execution; if egregious, raise to user for a 1-line override.

5. **Topbar avatar visibility for pre-Phase-4 users.** Some users may exist in localStorage with `leanshot_v4` but no Supabase session at all (never used AI Coach). For those users, the AvatarMenu should not render. Planner confirms the Phase 4 anon-mint-on-first-use behavior — if it covers all dashboard sessions, the no-session-at-all case is impossible by definition. If gaps exist, planner adds a fallback "Sign up" button in the Topbar's right-cluster.

6. **Onboarding TOTAL_STEPS change.** Researcher recommends incrementing 8 → 9 (new prompt step) OR keeping 8 but replacing step-7 single CTA with two CTAs — planner picks based on whether the ProgressIndicator should signal "you have one more step." **Recommend 8-step structure with the prompt as a CTA-pair on the final step** (no additional progress dot — feels less paywall-y).

7. **Error message `role="alert"` on inline field errors.** Existing `Input.tsx` `FieldShell` does NOT add `role="alert"` to the error `<p>` element. This means screen readers announce errors only on next field focus, not on submit-validation. Researcher recommends planner adds `role="alert"` to the `<p>` inside FieldShell when `error` is set (a one-line change to existing primitive). Cross-phase impact: improves a11y for all forms across the app, not just Phase 5.

8. **Marketing "Sign in" link sticky-header behavior.** Researcher's discretion call was "no scroll-state change." Planner confirms via existing Landing.tsx's sticky behavior; if the sticky header already has a scroll-state visual treatment, the Sign-in link inherits it.

9. **Magic-link UI prominence.** D-02 says password-primary; magic-link surfaces as a text link below the primary CTA on signin/signup. Researcher kept this minimal. If user research post-launch shows magic-link adoption is high, Phase 6+ can promote it to a button-equal-weight option.

10. **Verify-landing 1.5s auto-redirect duration.** Default chosen for screen-reader announcement timing. Planner may shorten to 1.0s if telemetry shows users wait through the redirect.
