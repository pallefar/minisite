<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| vanilla-cookieconsent banner → page JS | The banner is shipped Phase 22; we extend its callback surface. User input (consent click) crosses this boundary into application state. |
| `window.dispatchEvent` → arbitrary subscribers | Any script running on the same origin can `addEventListener('leanshot:consent-change')`. Treat the event as same-origin-public (no secrets in payload). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-41-01-01 | Information Disclosure | CustomEvent `detail.categories` payload | accept | Payload contains five booleans — already-public consent state visible via `localStorage.cc_cookie`. No PII, no tokens, no secrets. |
| T-41-01-02 | Tampering | Listener registered before banner load races the initial `onFirstConsent` emit | mitigate | `subscribeToConsentChange` callers (Plan 41-05 ConsentGatedEmbed) MUST also read `CookieConsent.acceptedCategory(...)` synchronously at mount — Assumption A3 in RESEARCH covers callback synchronicity, but mount-time read closes the race for late subscribers. Documented in 41-05 plan. |
| T-41-01-03 | Repudiation | Consent grant fires but is not persisted | accept | `upsertConsentRecord` runs BEFORE `emitConsentChange` per task action ordering — persistence happens first; emit reflects-or-precedes server write per existing Phase 22 contract. |
| T-41-01-04 | Spoofing | Malicious same-origin script dispatches a fake `leanshot:consent-change` event | accept | Same-origin-only XSS is the larger problem; if attacker has same-origin script execution, faking this event is the least of the concerns. Defense-in-depth: subscribers (Plan 41-05) ALSO read `CookieConsent.acceptedCategory(...)` at mount, so a fake event without a real consent-banner mutation cannot persist a state flip past the next genuine event. |
</threat_model>
