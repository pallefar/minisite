<!-- LWW loss-detection conditional (the load-bearing logic) -->

The condition under which the toast fires is NOT just "server's updated_at is newer than local's" — that fires on every routine cross-device propagation (e.g., user logs an injection on phone, laptop sees the postgres_changes INSERT 2s later, local was empty for that row so server is trivially newer). That is NOT a "conflict" — it's the happy path.

A TRUE LWW loss requires THREE conditions:

1. The row already exists locally (i.e., this is an UPDATE event, not an INSERT). OR if it's an INSERT, the local row exists with the SAME composite PK (rare; can happen if local generated the same uuid by chance, which shouldn't but let's not crash).
2. The local row has been EDITED locally in a way that produced (or would have produced) a queued sync op. We can detect this by checking `pendingOps` for a recent entry with matching `(table, key)`.
3. The incoming server row's `updated_at` is STRICTLY GREATER than the local row's `updated_at` (the LWW guard that's already in place).

If all 3 are true → the local edit lost to a server-side newer edit. Surface the toast.

The simplest reliable heuristic for condition #2: `state.pendingOps.find((op) => op.table === payload.table && op.key === payload.new.<pkField>)`. If a pending op exists when the server payload arrives → the local user's edit was racing with the server, and they lost. Even if the pending op was successfully flushed JUST before the realtime event arrived, this might miss the loss (race), but that's fine — the LWW resolution already picked the winner; the toast is informational.

**Edge case to AVOID FALSE POSITIVE:** if pendingOps contains an op that the sync engine HASN'T YET TRIED to flush (e.g., still offline), the toast firing is correct — the user's intent was to apply this edit, and the server already has a newer one. The user's queued op will overwrite the server when network returns (Phase 5 LWW): meaning the user ACTUALLY WINS in the end. But from the user's perspective at the moment the Realtime payload arrives, their visible local state is about to be replaced by the server state. Toast is still appropriate ("the server had newer; we kept the more recent — yours OR theirs").

For Phase 6 v1: keep the heuristic simple. Fire the toast whenever conditions 1+2+3 are true. If UAT surfaces false-positive complaints, refine in a follow-up.

**Step 1: Add `detectAndNotifyLwwLoss` helper in `src/lib/sync.ts`:**

Place near other helpers like `isPermanent4xx`:

```typescript
/**
 * Phase 6 D-11 — LWW conflict UX surface.
 *
 * Fires the "We kept your most recent edit." toast when a local edit was about
 * to be flushed (still in pendingOps) AND the server emits a Realtime payload
 * with a strictly newer `updated_at`. The LWW resolution itself is unchanged;
 * this only surfaces the user-facing notification on the losing device.
 *
 * Heuristic — 3 conditions:
 *   1. server.updated_at > local.updated_at (strictly newer)
 *   2. local row has a queued pendingOp matching (table, key) → local edit lost
 *   3. local row exists (else there's no "loss" — it's just an INSERT propagation)
 *
 * The toast is `info` kind, ~5000ms duration (Plan 06-01 enabled durationMs
 * on the toast state). Tap-to-dismiss is enabled if Plan 06-01 added that.
 *
 * Returns true if the toast was emitted; false otherwise. Tests assert on the
 * return value to keep the test independent of toast component implementation.
 */
export function detectAndNotifyLwwLoss(
  table: string,
  key: string,
  serverUpdatedAt: string | undefined,
  localUpdatedAt: string | undefined,
): boolean {
  if (!serverUpdatedAt || !localUpdatedAt) return false;
  const serverTs = new Date(serverUpdatedAt).getTime();
  const localTs = new Date(localUpdatedAt).getTime();
  if (Number.isNaN(serverTs) || Number.isNaN(localTs)) return false;
  if (serverTs <= localTs) return false; // not a loss; local wins or tie

  const state = useStore.getState();
  const hadPendingEdit = (state.pendingOps ?? []).some(
    (op) => op.table === table && op.key === key,
  );
  if (!hadPendingEdit) return false; // vanilla cross-device propagation, no conflict UX

  state.notifyLwwLoss(table, key);
  return true;
}
```
