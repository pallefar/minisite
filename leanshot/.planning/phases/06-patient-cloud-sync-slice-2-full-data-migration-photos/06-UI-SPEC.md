## Typography

The codebase declares 12 type scale steps in `src/index.css:84-110`. Phase 6 uses a deliberately constrained **4-size subset** matching Phase 5's pattern:

| Role | Size | Weight | Line Height | Token | Where used in Phase 6 |
|------|------|--------|-------------|-------|----------------------|
| Body | 14px | 400 (regular) | 1.55 | `text-[14px]` | Migration modal description copy; conflict-toast body text |
| Label / count | 13px | 600 (semibold), tabular nums | 1.5 | `text-[13px] font-semibold tabular-nums` | Entity row name + count column ("Injections" / "47 of 47") |
| Heading | 16–22px | 700 (bold) tracking-tight | 1.15–1.35 | `text-[16px] md:text-[22px] font-bold tracking-tight` | Migration modal title ("Migrating your data") |
| Caption / hint | 11–12px | 400/600 | 1.4 | `text-[12px] text-[var(--color-text-tertiary)]` | Counter row sub-status ("Done" / "Pending" / "Resuming…") |

**Weights declared: 2 net-new** (none — 400/600/700 are already in use across `Card`, `Button`, `Toast`, Phase 5 auth components).

**Tabular numerals are MANDATORY for counter rows.** Without `tabular-nums`, count text jitters horizontally as digits update from `9 → 10 → 11`. Use Tailwind utility `tabular-nums` or CSS `font-variant-numeric: tabular-nums`. JetBrains Mono is the fallback if precision-critical (we expect Inter's tabular-num feature is enough; planner can override).

**Forbidden in Phase 6:**

- `text-[10px]` for counter rows — too small per CLAUDE.md accessibility-first mandate. The 10px caption convention is reserved for photo-grid date overlay only (existing in `BodyTab.tsx:267`).
- `text-display` / `text-5xl` / `text-4xl` / `text-3xl` — marketing-only sizes; the migration modal is utilitarian.
- New font families.

## Component Spec

Phase 6 ships **2 net-new component surfaces** plus **3 modifications to existing surfaces**. Each spec below covers layout, typography, spacing, states, animations, accessibility, and reduced-motion fallback.

### 1. MigrationModal (`src/components/sync/MigrationModal.tsx`) — NEW

**Purpose:** Foreground blocking modal that gates dashboard access on first sign-in for an existing `leanshot_v4` user, per D-01. Shows per-entity migration progress, supports resume (D-02), and offers an escape hatch ("Continue with sync running") so the user is not held hostage if migration of the largest entity (photos) is slow.

**Component composition:** Built on existing `Modal` primitive with `dismissible={false}` and `hideClose` (default close X hidden — escape happens via explicit CTAs, NOT the X). Body content = list of `MigrationEntityRow` (per-entity), then completion-state or escape-state CTAs.

**Modal sizing:** `size="md"` (max-w-md ≈ 448px). Wider than auth (440px) by a hair to fit two-column "name | count" rows comfortably on the longest entity name ("Supplements" or "Mood entries"). Mobile: `mobileFullscreen={false}` — the modal is a bottom-sheet on mobile per the existing Modal mobile-fullscreen behavior at `Modal.tsx:88-92` (rounds top corners only, slides up from bottom).

**Layout:**

```
┌────────────────────────────────────────────────┐
│ [no close X — hideClose=true]                  │
│                                                 │
│  Migrating your data                ← H1 16px bold mobile / 22px desktop
│  Saving your history to your account.          │ ← 14px text-secondary
│  This should take less than a minute.          │
│                                                 │
│  ┌──────────────────────────────────────────┐  │
│  │ Injections          47 of 47   [▓▓▓▓▓▓] │  │ ← MigrationEntityRow (in-progress)
│  ├──────────────────────────────────────────┤  │
│  │ Weights             ✓  84       (done)   │  │ ← MigrationEntityRow (done)
│  ├──────────────────────────────────────────┤  │
│  │ Photos              —                    │  │ ← MigrationEntityRow (pending)
│  ├──────────────────────────────────────────┤  │
│  │ ...                                       │  │
│  └──────────────────────────────────────────┘  │
│                                                 │
│  [Continue with sync running]   ← Button ghost  │
└────────────────────────────────────────────────┘
```

After all rows complete, the body collapses to a completion state:

```
┌────────────────────────────────────────────────┐
│       ╭───────╮                                │
│       │   ✓   │   ← size-12 circle, success bg │
│       ╰───────╯                                │
│                                                 │
│  All done                            ← H1      │
│  Your history is safe in the cloud.            │ ← 14px text-secondary
│  You can now sync across devices.              │
│                                                 │
│  [Continue to dashboard]    ← Button primary block │
└────────────────────────────────────────────────┘
```

**Entity row anatomy** (`MigrationEntityRow` subcomponent):

```
┌────────────────────────────────────────────────────────────┐
│ [icon] [Entity name 13px semibold]  [count 13px tabular]  │ ← row 1 (flex justify-between)
│        [ProgressBar thin 3px full-width]                   │ ← row 2 (in-progress only)
└────────────────────────────────────────────────────────────┘
```

| Row state | Left icon | Name color | Count format | ProgressBar |
|-----------|-----------|------------|--------------|-------------|
| Pending | `<Circle />` 16px `text-tertiary` outline (or omit icon entirely) | `text-secondary` | `—` em-dash | Not rendered |
| In-progress | `<Loader2 />` 16px `text-primary` `animate-spin` | `text-primary` (full strength) | `{n} of {total}` | `thickness="thin"` (3px), `color="var(--color-primary)"` |
| Complete | `<Check />` 16px `text-success` | `text-secondary` | `{total}` | `thickness="thin"`, `color="var(--color-success)"`, fixed at 100% (rendered briefly for transition, then can collapse) |
| Error | `<AlertCircle />` 16px `text-danger` | `text-danger` | `{n} of {total}` | hidden; replaced with inline `Retry` text-link |

**Row spacing:**
- Vertical between rows: `py-2.5` (10px top + 10px bottom) — denser than `gap-4` to fit 11 rows in viewport without scroll on a 13" laptop. Optional 1px separator (`border-t border-[var(--color-border)]`) for visual rhythm.
- Internal horizontal gap: `gap-3` (12px) between icon-name-count.
- ProgressBar margin-top from row 1: `mt-1.5` (6px).

**Row order (D-01 — size-descending):**

Researcher recommendation for ordering, since CONTEXT D-01 says "biggest table first" but doesn't pre-specify the order for a fresh `leanshot_v4` user: planner SHOULD compute order at runtime from the actual snapshot row counts (e.g., `Object.entries(snapshot).sort((a,b) => b[1].length - a[1].length)`). If row counts tie or are unknown ahead of time, fall back to this static ordering by typical v2 user volume:

1. **Photos** (typically the largest by upload time — base64 decode + canvas compress + Storage upload is serial per D-09)
2. **Injections**
3. **Weights**
4. **Meals**
5. **Workouts**
6. **Supplements**
7. **Mood entries**
8. **Sleep entries**
9. **Symptoms**
10. **Vials**
11. **Settings** (singleton — always tiny)

**Modal states:**

| State | Trigger | Visual |
|-------|---------|--------|
| `idle` (not migrating) | No `migration_state` in store, OR `migration_state.complete === true` | Modal NOT rendered |
| `migrating-fresh` | First sign-in for existing v4 user; `migration_state` just initialized | Modal open with title "Migrating your data"; all rows pending → in-progress as queue drains |
| `migrating-resume` | Sign-in finds `migration_state.complete !== true` AND at least 1 entity already `complete` | Modal open with title "Resuming migration"; completed rows already show ✓; in-progress row picks up from saved progress |
| `complete` | All entities `complete` | Body swaps to completion-state layout (centered success badge + "All done" + "Continue to dashboard" primary CTA). Modal auto-dismisses after 3000ms via `setTimeout` IF user has not interacted, OR closes on CTA click — whichever first. *(See Open Questions for auto-dismiss arbitration.)* |
| `error-corrupted-state` | `migration_state` corrupted detection rule fires (D-02 Claude's discretion) | Body shows error banner ABOVE the row list; `Retry migration` primary CTA replaces "Continue with sync running" |
| `escape-soft-dismiss` | User clicks "Continue with sync running" | Modal closes; info-kind toast `Migration continuing in the background.`; dashboard mounts; next sign-in finds `migration_state.complete !== true` and re-opens the modal in resume mode (D-02 behavior) |

**Animations:**

- Modal mount: existing `Modal` framer-motion entrance (Modal.tsx:94-97 — `y: 24 → 0`, `opacity: 0 → 1`, `scale: 0.98 → 1`, 300ms `ease-out-quart`).
- ProgressBar fill: existing `transition-[width] duration-500 ease-out` (ProgressRing.tsx:111) — 500ms width transition between progress values. Visually buttery; no extra work.
- Row state transition (pending → in-progress → complete): swap icon + text color + ProgressBar visibility. Use framer-motion `<AnimatePresence mode="wait">` ONLY on the icon swap (`<Loader2 />` → `<Check />`) with a 150ms fade. The ProgressBar disappears with a 200ms collapse (`height: 3 → 0`). Optional polish — planner can defer if budget tight.
- Completion-state body swap: framer-motion `<AnimatePresence mode="wait">` between row-list and "All done" centered layout, 250ms cross-fade.

**Reduced motion:**

- Row state transitions: instant icon/text swap, NO ProgressBar width transition (set inline `transition: 'none'`).
- Body swap to completion: instant (no AnimatePresence transition).
- Modal mount: opacity-only fade per existing `index.css:485` reduced-motion block.

**Accessibility:**

- Existing `Modal` provides `role="dialog"` + `aria-modal="true"` + auto-focus management.
- Modal title is the `aria-label` (Modal.tsx:84 — picked up from `title` prop string).
- Row list: render as `<ol role="list" aria-label="Migration progress">`. Each row is `<li>` with `aria-busy={state === 'in-progress'}` and an `aria-label` like `Injections: 47 of 47 uploaded, in progress`.
- Live region: wrap the entire row list in `<div aria-live="polite" aria-atomic="false">` so screen readers announce each row's completion. **DO NOT** announce every count tick (that would be deafening for 200-meal users); instead, fire announcements only on state TRANSITIONS (pending→in-progress, in-progress→complete, *→error). Implementation pattern: a hidden `<span role="status">` that gets its text replaced only on transition events, NOT on count updates.
- Keyboard: Tab focuses the only visible button ("Continue with sync running" during migration, "Continue to dashboard" on complete, "Retry migration" on error). ESC is disabled (Modal `dismissible={false}` → ESC handler in Modal.tsx:59 is a no-op).
- Focus on mount: first focusable element (the escape CTA). On completion-state transition, focus moves to the primary CTA automatically.

**Bundle-size note (per D-12 CI hardening):** This component MUST be dynamic-imported via `src/lib/sync-defer.ts` — it ships ONLY for users who actually need to migrate (existing v4 users on first sign-in). New signups never load it. The planner SHOULD verify this stays out of the main bundle via the 50 kB gzip CI assertion (D-12 reference: bundle-size guard already in `.github/workflows/ci.yml`).

### 2. ConflictToast — REUSES `Toast` primitive (D-11)

**Not a new component.** Phase 6 fires the existing `<Toast>` with kind `info` and the D-11 copy via the existing `showToast` action.

**Composition delta from existing Toast:**

The current `Toast.tsx:13` hardcodes a 2400ms auto-dismiss. Phase 6 needs ~5000ms for this informational message because it has no recovery affordance and the user needs time to read it on a small phone screen while doing something else.

**Implementation guidance for planner:**

Add an optional `duration` field to the toast state shape in `store.ts`:

```ts
// store.ts ToastState (current — implicit 2400ms)
toast: { id: number; message: string; kind: 'success' | 'error' | 'info' } | null;

// store.ts ToastState (Phase 6)
toast: { id: number; message: string; kind: 'success' | 'error' | 'info'; durationMs?: number } | null;
```

And update `Toast.tsx:13`:

```ts
const t = setTimeout(dismiss, toast.durationMs ?? 2400);
```

Default behavior unchanged; conflict toast passes `durationMs: 5000`.

**Visual:** existing `Toast` `info` kind — `bg-[var(--color-text)] text-[var(--color-bg)]` (inverse contrast — dark pill on light background, light pill on dark background). `<Info />` icon left of text. Pill shape (`rounded-pill`). Position: bottom-center (`fixed left-1/2 -translate-x-1/2`, `bottom-[calc(96px+env(safe-area-inset-bottom,0))] md:bottom-10` — already correct in Toast.tsx:30).

**Why info, not warning or error:**

- D-11 explicit: "this is informational, not a failure." LWW worked exactly as designed.
- Warning yellow would imply user action is needed (none is needed).
- Error red would imply something broke (nothing did).
- The existing `info` kind's neutral high-contrast pill reads as "FYI" tone — correct.

**Dismissibility:** The current `Toast.tsx` is auto-dismiss only, no tap-to-dismiss affordance. Phase 6 SHOULD add a tap-to-dismiss handler — the entire pill becomes clickable, calling `dismissToast()` on click. Add `cursor-pointer` class and a small fade-on-hover. *(See Open Questions — planner confirms whether to bundle this into Phase 6 or defer to a later phase.)*

**Accessibility:**

- `role="status"` + `aria-live="polite"` (existing).

### 4. AvatarMenu Sync-Status Dot — MODIFIED (D-discretion, recommended INCLUDE)

**Existing surface:** `AvatarMenu.tsx:192` already renders a 10px status dot at the avatar's bottom-right, currently bound to email-verified state:

```ts
const statusDotClass = verified ? 'bg-[var(--color-success)]' : 'bg-[var(--color-warning,#a36a00)]';
```

**Phase 6 recommendation:** Repurpose this dot as a **multi-state sync indicator** that supersedes verification-only signal. Rationale:

- The status-dot affordance already exists — zero net-new visual primitive.
- Phase 5's verification state still matters but is subsumed: an unverified user is implicitly offline-only (can't sync). The new "offline / sync-error / syncing / synced" state space includes "unverified" as a synonym for "offline-only — can't sync until verified."
- Phase 6's cloud-sync surfaces (4 surfaces total) deserve at-a-glance visibility from the dashboard's most persistent UI element (the avatar in the topbar).
- Cost: ~15 lines of TS + 4 lines of CSS. Negligible.

**State logic (planner discretion on exact derivation):**

```
1. Email unverified → dot = warning (existing behavior preserved; AT label: "verification pending")
2. Email verified + queued ops in pendingOps + offline (!navigator.onLine) → dot = warning, AT label: "offline, changes will sync"
3. Email verified + sync engine actively flushing → dot = info (--color-primary aliased), pulse animation (1.4s ease-in-out), AT label: "syncing"
4. Email verified + sync engine errored (last flush returned error) → dot = danger, AT label: "sync error, tap to view"
5. Email verified + no queued ops + last sync successful → dot = success, AT label: "all synced" (this becomes the new resting state)
```

**Sync-error dot tap behavior:** When dot is `danger` (state 4), tapping the avatar opens the menu and adds a one-line error row at the top of the dropdown: `Last sync failed — Retry`. This row is only present when state = error. Not a new dropdown menu item type — just a contextual prefix.

**Pulse animation (syncing state):**

```css
@keyframes sync-pulse {
  0%, 100% { transform: scale(1); opacity: 1; }
  50%      { transform: scale(1.25); opacity: 0.65; }
}
.sync-status-dot--syncing { animation: sync-pulse 1.4s var(--ease-in-out-quart) infinite; }
```

Respects `prefers-reduced-motion` — disable the pulse, leave the dot solid color.

**If planner DEFERS this surface to Phase 7:** then Phase 6 leaves AvatarMenu untouched, and the email-verified-only dot ships as-is. The migration modal + conflict toast cover the at-a-glance "something is happening" need on their own. Defer is acceptable; no Phase 6 success criterion depends on this dot. *(Captured in Open Questions.)*

## Open Questions (for planner / user)

These are not blocking the spec — defaults are spelled out — but the planner / plan-checker MAY want to confirm before authoring tasks:

1. **Migration modal escape hatch wording.** Current default: `Continue with sync running`. Alternative considered: `Skip for now` (worse — implies user can opt out, which they can't — migration WILL re-open next sign-in per D-02). `Continue in background` (close but "background" overloads the JS-runtime word). Recommend keeping the default.

2. **Migration completion auto-dismiss timing.** Default: 3000ms auto-dismiss on complete-state unless user clicks Continue first. Open to 5000ms if planner thinks 3s is too quick to register the "All done" success moment. CONTEXT D-01 said "auto-dismiss after N seconds OR explicit Done button" — both, with the explicit CTA being primary.

3. **Conflict toast duration override.** Default 5000ms (vs `Toast`'s current 2400ms). Implementation requires adding `durationMs?: number` to the toast state. The planner may instead choose to leave the existing 2400ms global default and accept that "We kept your most recent edit" gets ~2.4s reading time. Recommend the 5s override — it's a one-field store change and tested patterns.

4. **Tap-to-dismiss on conflict toast.** Default: ADD (entire pill clickable, dismissToast on click, `cursor-pointer`). Alternative: leave non-clickable. Recommend ADD; <10 LoC change to `Toast.tsx`.

5. **AvatarMenu sync-status dot (Section 4 of component spec).** Default: INCLUDE in Phase 6 — supersedes the verification-only dot with a richer 4-state sync indicator. Cost ~30 LoC. Alternative: defer to Phase 7 and keep Phase 5's verification-only dot. Either is acceptable; no Phase 6 SC depends on it.

6. **Skeleton `prefers-reduced-motion` fix.** Discovered during this spec: `Skeleton.tsx` does NOT respect prefers-reduced-motion (its shimmer keyframe runs unconditionally). Phase 6 SHOULD fix this since it introduces new Skeleton usage on photo tiles. Planner: fold into the BodyTab photo-grid plan, or split into a tiny separate plan. Recommend fold-in.

7. **Counter row ordering when row counts are unknown ahead-of-time.** Default: planner computes order at runtime from snapshot row counts (size-descending per D-01). Fallback static order spelled out in Section 1. If planner discovers an edge case (e.g., photo count 0 but injection count 200 — what does "size" mean?), the recommended tiebreaker is the static fallback order.

8. **Migration error visual pattern.** D-02 mentions "if `migration_state` itself is corrupted" but doesn't pre-specify whether per-entity errors get inline retry vs only the whole-migration retry. Default in this spec: per-entity errors show inline `Retry` text-link on that row (re-tries just that entity's queue), AND a global error banner appears at the top of the modal listing all failed entities. Top-level "Retry migration" CTA only appears on the `migration_state` corrupted path (rare). Planner can simplify to whole-migration-retry-only if per-entity retry is too complex for the queue substrate (D-08).
