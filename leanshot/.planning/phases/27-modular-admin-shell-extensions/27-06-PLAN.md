Worker contract:

  POST handler at supabase/functions/admin-bulk-job-worker/index.ts:
  1. checkServiceRoleBearer → 401 if missing
  2. Claim up to N=3 pending jobs in one transaction:
     `update admin_bulk_jobs
        set status='running', claimed_by=gen_random_uuid()::text, claimed_at=now()
        where id in (
          select id from admin_bulk_jobs where status='pending' order by created_at limit 3 for update skip locked
        )
        returning *`
     (skip_locked prevents two workers claiming the same job if cron fires twice within 1 min)
  3. For each claimed job: process_job(job)
     - For each chunk of 100 in target_user_ids:
       - Execute per-action mutation (same logic as sync RPC path — DUPLICATED HERE in TS since the sync RPC is plpgsql; alternative: call a `admin_bulk_action_process_chunk(job_id, chunk_offset, chunk_size)` SECDEF RPC that does the work in plpgsql for code reuse; RECOMMENDED — keeps action logic single-sourced. Add this RPC in this plan's Task 1)
       - Per-row log_admin_action
       - Update rows_completed += chunk_size
       - Catch per-row exception → append to error_log jsonb array
     - On completion: set status='completed', completed_at=now()
     - On any catastrophic failure (RPC unreachable, etc.): set status='failed' + error_log
  4. Return jsonResponse({claimed:N, completed:M, failed:K})

  Idempotency: if a worker dies mid-job, the cron re-fires next minute; the job is still status='running' so won't be re-claimed by the `where status='pending'` filter. SOLUTION: add a reclaim step BEFORE the claim step: `update admin_bulk_jobs set status='pending', claimed_by=null, claimed_at=null where status='running' and claimed_at < now() - interval '5 minutes'` — reclaims stuck jobs. The chunked work itself doesn't need to be idempotent within a single run because partial progress is tracked in rows_completed; on reclaim, the worker resumes from rows_completed offset.

New SECDEF RPC contract (for chunked processing):

  admin_bulk_action_process_chunk(p_job_id uuid, p_chunk_offset int, p_chunk_size int) returns jsonb
    - gated on service_role (NOT is_admin_at_least — only the worker calls this; service_role bypasses auth.uid())
    - reads job row, slices target_user_ids[p_chunk_offset:p_chunk_offset+p_chunk_size]
    - executes per-action mutation (switch on action_type)
    - returns {processed:int, errors:jsonb[]}
    - This RPC's body is essentially the same plpgsql logic that admin_bulk_action_execute (Plan 27-01) uses for the sync path — but parameterized for an arbitrary chunk

Cron contract:
- `select cron.schedule('admin-bulk-job-worker', '* * * * *', $$ select net.http_post(url := '.../functions/v1/admin-bulk-job-worker', headers := {Authorization:'Bearer ' || vault.decrypted_secrets.<key>}, body := '{}'::jsonb) $$);` — every 1 minute
- Collision check: every-minute schedule collides at minute 0 with most other crons but pg_cron parallelizes across jobnames — accept

    - Stops polling when status in ('completed','failed')
    - Returns BulkJobState shape for the UI
