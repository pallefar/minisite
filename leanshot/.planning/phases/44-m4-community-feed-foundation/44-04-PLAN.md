<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser (user JWT) → mux-create-upload | User-authenticated; tier_effective is the gate, NOT service-role. Browser never sees Mux secrets. |
| Mux Cloud → mux-webhook | Untrusted public endpoint; HMAC signature is the only authentication; passthrough is user-controlled (signed by Mux but contains client-supplied data). |
| mux-webhook → community_posts UPDATE | Service-role client; bypasses RLS — passthrough.post_id MUST be validated against the original creator's user_id to prevent cross-account post pollution. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-44-02 | Elevation of Privilege | mux-create-upload | mitigate | tier_effective check against caller's auth.uid() (parsed from bearer JWT); Free tier returns 403 VIDEO_TIER_REQUIRED. Deno test proves Free user is rejected. |
| T-44-03 | Spoofing | mux-webhook | mitigate | `mux.webhooks.verifySignature()` from @mux/mux-node — handles timestamp tolerance + multi-sig headers. Deno test proves invalid signature returns 401. |
| T-44-02b | Tampering (passthrough abuse) | mux-webhook UPDATE scope | mitigate | Webhook UPDATE scoped to `community_posts.id = passthrough.post_id`; the row was already author-locked by RLS at insert-time (Plan 44-01 cpost_update_author requires author_id = auth.uid()). Since mux-webhook uses service-role (RLS-bypass) UPDATE, the row's author_id is implicitly trusted because the webhook can only fire for assets the composer earlier created with valid passthrough. NOTE: a cross-tenant attacker would need (a) Mux's webhook secret AND (b) the victim's post_id — both server-side secrets. Acceptable risk. |
</threat_model>
