<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser (user JWT) → mux-create-upload | User-authenticated; tier_effective is the gate, NOT service-role. Browser never sees Mux secrets. The user_id baked into passthrough is the server-trusted auth.uid() — NOT a client-supplied field. |
| Mux Cloud → mux-webhook | Untrusted public endpoint; HMAC signature is the only authentication; passthrough was created server-side by mux-create-upload from auth.uid() + post_id, so its values are trusted once HMAC verifies. |
| mux-webhook → community_posts UPDATE | Service-role client; bypasses RLS — UPDATE is scoped by `id = passthrough.post_id` (the row was already author-locked by RLS at insert-time via Plan 44-01 cpost_update_author). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-44-02 | Elevation of Privilege | mux-create-upload | mitigate | tier_effective check against caller's auth.uid() (parsed from bearer JWT); Free tier returns 403 VIDEO_TIER_REQUIRED. Deno test proves Free user is rejected. |
| T-44-03 | Spoofing | mux-webhook | mitigate | `mux.webhooks.verifySignature()` from @mux/mux-node — handles timestamp tolerance + multi-sig headers. Deno test proves invalid signature returns 401. |
| T-44-02b | Tampering (passthrough abuse) | mux-webhook UPDATE scope | mitigate | UPDATE scoped to `community_posts.id = passthrough.post_id`. Passthrough was server-minted by mux-create-upload (signed implicitly by Mux's HMAC), not client-supplied at webhook-time. Missing/malformed passthrough → handler logs + 200 + skips UPDATE (no loop). Cross-account write requires (a) Mux webhook secret AND (b) the ability to mint a fake passthrough referencing another user's post_id — both server-side secrets. Acceptable risk. |
</threat_model>
