## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User input → sanitizeCommunityMarkdown | All community post/comment bodies pass through this single chokepoint before render |
| Browser → Storage upload | uploadCommunityMedia performs client-side validation as the UX gate; storage RLS + bucket file_size_limit + MIME whitelist are the authoritative gates (Plan 44-01) |
| tier_effective view → client | readTierLabel is read-only against tier_effective; never used to write tier state |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-44-05 | Tampering (XSS) | dompurify-config.ts | mitigate | Explicit ALLOWED_TAGS allowlist; FORBID_TAGS for img/script/iframe/style/object/embed/base/form; afterSanitizeAttributes hook forces target=_blank rel=noopener noreferrer on anchors AND strips non-http(s) href values. Unit tests prove `<script>`, `<img>`, `javascript:`, `<iframe>` cases all stripped. |
| T-44-04 | Tampering (storage path traversal) | community-storage.ts uploadCommunityMedia | mitigate | Client constructs path as `${userId}/${postId}/${crypto.randomUUID()}.${ext}`; storage RLS (Plan 44-01) enforces `(storage.foldername(name))[1] = auth.uid()::text` so even a tampered client cannot write under another user's prefix. |
| T-44-06 | DoS via mention spam | mention-parse.ts parseMentions | mitigate | Server-side dedupe via Set; client-side parse is informational only — community_post_mentions PRIMARY KEY (post_id, user_id) is the authoritative idempotency gate. notification_category_config.daily_cap=20 (Plan 44-02). |
</threat_model>
