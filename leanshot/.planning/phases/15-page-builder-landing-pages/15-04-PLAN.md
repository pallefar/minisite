<objective>
Complete the thinnest end-to-end MVP slice of the Page Builder: a `is_staff` user can scaffold a landing page with core blocks in the editor, Save it (append-only revision), Publish it (re-point pointer + revalidate), and a public visitor then sees the rendered page at `/{slug}`.

This plan delivers the two write-side Edge Functions (`page-save`, `page-publish`) and the minimal editor shell (`PageListView`, `PageEditorView`, `BlockTreePanel`, `PropertyPanel`, and the Hero/CTA/Footer block components). It builds on Wave 1 (live schema + `is_staff` + bundle/CSP/routing config) and Wave 2's `page-render` + `block-schema.ts` (15-03).

Purpose: After this plan, the loop "staff scaffolds → saves → publishes → visitor sees `/{slug}`" works. Slice 2 (15-05..09) thickens with the remaining 9 blocks, live PreviewPane, templates, asset library, SEO, versioning UI, embeds, and lead capture.
Output: 2 deployed-ready Edge Functions + 1 editor route branch + 5 editor/block components + 1 browser API module + Deno + vitest + Playwright coverage.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Public browser → `page-save` / `page-publish` Edge Functions | Untrusted JWT + JSON body crosses here. The functions are JWT-authed (`verify_jwt = true`) AND must independently re-verify `is_staff` server-side. |
| `/admin/pages/*` client route guard → editor UI | The client route guard (`opts.user ? ... : 'auth'` in `selectView`) is defense-in-depth ONLY — it is NOT the security boundary. A non-staff authenticated user can reach the editor UI; the real gate is the Edge Functions + RLS. |
| Edge Function → Postgres (`landing_pages`, `landing_page_revisions`) | Service-role admin client bypasses RLS to read the `is_staff` gate and write rows. All writes must be parameterized via the supabase-js client (no string SQL). |
| `page-save` slug input → `landing_pages.slug` / `vercel.json` `/{slug}` routing | A malicious staff user could attempt to register a slug shadowing an app path route (`/admin`, `/clinic`, `/share`). The reserved-slug denylist + slug-format regex are the mitigation, enforced server-side at save. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-15-04-01 | Elevation of Privilege | `page-save` / `page-publish` Edge Functions | mitigate | Server-side `is_staff` gate: after JWT→user resolution, `profiles.select('is_staff')` via service-role client; `!is_staff` → 403. Deno Test 3 (page-save) + Test 2 (page-publish) prove a non-staff JWT is rejected with 403 and no write occurs. Client route guard is explicitly NOT trusted. |
| T-15-04-02 | Spoofing | `/admin/pages/*` route guard | mitigate | Client `selectView` guard checks `user` presence and is documented in-code as defense-in-depth only. Authorization is enforced exclusively by the Edge Functions + RLS; a spoofed/forged client state cannot write data. |
| T-15-04-03 | Tampering | `page-save` slug input → app routing | mitigate | Server-side reserved-slug denylist (`RESERVED_SLUGS` imported/mirrored from `block-schema.ts`) + slug-format regex (`^[a-z0-9]+(?:-[a-z0-9]+)*$`), both enforced in `handleSave` for NEW pages → 400 `reserved_slug` / `invalid_slug`. Deno Tests 5 + 7 prove rejection. Prevents a staff user shadowing `/admin`, `/clinic`, etc. |
| T-15-04-04 | Tampering / Repudiation | `landing_page_revisions` append-only invariant | mitigate | `page-save` only `.insert()`s into `landing_page_revisions` — never `.update()`/`.delete()`. Deno Test 6 asserts no UPDATE/DELETE call on the fake admin. Append-only history is non-repudiable (every save is a distinct, immutable, `created_by`-attributed row). 15-01 owns the DB-level invariant test. |
| T-15-04-05 | Information Disclosure | Edge Function error responses | mitigate | All error paths return a short opaque code (`{ error: 'forbidden' }`, `{ error: 'internal_error' }`) — never raw exception text or stack traces. Top-level try/catch logs `console.error('[page-save] ...', err.message)` server-side only, mirroring `stripe-checkout`. |
| T-15-04-06 | Denial of Service | `page-publish` revalidation HEAD `fetch` | accept | The outbound `x-prerender-revalidate` HEAD is best-effort and wrapped in try/catch (Deno Test 5). A hung/failing Vercel endpoint cannot block or fail the publish (DB pointer move already committed). No retry loop. Low risk: the call is staff-triggered, not visitor-triggered, so it is not an amplification vector. |
| T-15-04-07 | Tampering (XSS) | Block `content` fields → future `page-render` HTML | transfer | This plan stores block `content` as JSONB only; it does not render to HTML. The XSS surface is `page-render`'s `renderBlock()` (15-03), which the RESEARCH "Don't Hand-Roll" guidance designs out by only emitting known template strings for known block types — no `innerHTML` from user data. This plan's responsibility: keep `content` as structured JSONB (no HTML strings), which it does. |
