# v1.4 Launch-Readiness Gaps

> Definition of "blocker": cannot launch to paying customers next month without active legal/financial/customer-trust exposure.
> Definition of "hard-debt": launch is possible, but day-one operational pain (high pager noise, founder time-sink, lost revenue) within 30 days.
> Definition of "nice-to-have": post-launch polish; surface to v1.5 backlog, do NOT add to v1.4 roadmap.

Audit was prioritized against the 10 dimensions in the brief. The 4 dimensions with the **most material gaps** (Security beyond HIPAA / Legal-Compliance / Payment Resilience / Onboarding-Activation) get fullest treatment below. Observability + Performance + Marketing + Support are spot-checked; Internationalization + App-Store are covered by the existing v1.4 carry-over backlog (Phase 32-06 + Phases 16-21 + Phase 34 Apple OAuth) and noted only for completeness.

## 1. Security posture beyond HIPAA controls

Audited against: `src/components/auth/`, `supabase/functions/_shared/`, MFA implementation in `src/components/admin/SetupTotpPage.tsx`, share-token brute-force protection in `supabase/functions/share/index.ts`.

### Gap 1.1 — Consumer-account MFA / TOTP is absent (admin-only today)
- **What:** TOTP enrolment is implemented for `is_staff` admins (`SetupTotpPage`, AAL2 step-up enforced in `AdminLayout.tsx`). There is no surface for B2C patients or clinic clinicians to enable MFA on their own account. Stored health data + injection history is highly sensitive — account-takeover via reused password is the #1 user-trust risk for any health vertical post-launch.
- **SEVERITY:** hard-debt (launch possible; clinics in particular will ask "can my users enable 2FA?" within day 1 of B2B sales conversations)
- **EFFORT:** sub-phase (Supabase Auth `mfa.enroll/challenge/verify` already wired for admins — reuse in a `/settings/security` consumer surface)
- **DEPENDS_ON:** new

### Gap 1.2 — No global auth-attempt rate-limit / brute-force lockout on sign-in
- **What:** Searched `supabase/functions/` for sign-in throttling — share-token endpoint has per-share `failed_attempts_count` (good), lead-capture has IP-windowed 429 (good), but consumer **sign-in** itself relies entirely on Supabase Auth's built-in protections. There is no per-IP/per-email lockout layer, no credential-stuffing detector, no PostHog event firing on N consecutive failed attempts. With public app at `app.leanshot.app` after launch this becomes a low-cost attack surface.
- **SEVERITY:** hard-debt (Supabase has default protections, but no app-level detection/alerting)
- **EFFORT:** single plan (Edge Fn middleware + `auth_attempts_log` table + PostHog alert + cookie banner mention)
- **DEPENDS_ON:** new

### Gap 1.3 — Secrets-rotation policy + key inventory is undocumented
- **What:** v1.3 ships ~30+ Function Secrets (Stripe, Anthropic, Resend, Mux, RevenueCat, Calendly OAuth ×5, Better Stack, Sentry DSN, PostHog Personal API, SHARE_TOKEN_SECRET, vault `service_role_key`, OpenAI for embeddings, Meta/Google/TikTok ad tokens, etc.) but there is no `.planning/runbooks/secrets-rotation.md` documenting (a) what each secret guards, (b) rotation cadence, (c) the rotation procedure, (d) blast-radius if leaked. Operators rotating one of these at 3 AM during an incident will not have a runbook to follow.
- **SEVERITY:** hard-debt (no acute exposure, but ANY leak event becomes a 4-hour scramble instead of a 30-min runbook execution)
- **EFFORT:** single plan (inventory + write `secrets-rotation.md` runbook)
- **DEPENDS_ON:** new

### Gap 1.4 — Vercel + Supabase rate-limit/abuse posture isn't documented or load-tested
- **What:** No documented DDoS / abuse posture for the Vercel edge (rate limits per route?) or Supabase Edge Fn cold-start ceiling. The `/api/og/` route, `affiliate-impression`, `lead-capture`, and `traffic-attribution-recorder` are all public unauthenticated endpoints that, under abuse, would burn Supabase compute quota directly. Each has SOME protection (some rate-limit at the row level) but there's no end-to-end "if X traffic floods in, here's what happens and here's our floor" assessment.
- **SEVERITY:** hard-debt (the day someone posts a LeanShot link to HN, this matters)
- **EFFORT:** single plan (k6 load test against `/api/og/`, `affiliate-impression`, `page-render` + Vercel rate-limit config + Edge Fn timeout audit)
- **DEPENDS_ON:** new

### Gap 1.5 — Sentry DSN may be missing in production (warned by `_shared/sentry.ts`)
- **What:** `supabase/functions/_shared/sentry.ts` has the line `console.warn('[sentry] SENTRY_DSN missing — captureException is a no-op until set.')`. If `SENTRY_DSN` is not set as a Function Secret in production, all 116 Edge Fns silently swallow exceptions. Need to verify `SENTRY_DSN` is present **for Edge Fns specifically** (not just for the front-end vite `@sentry/react`).
- **SEVERITY:** hard-debt (likely already set — verify, don't assume; observability blind-spot if not)
- **EFFORT:** verification only (`supabase secrets list | grep SENTRY_DSN`) → if absent, single plan to set + add CI guard
- **DEPENDS_ON:** new (consolidate into UAT phase pre-flight)

## 2. Legal / compliance / trust

Audited against: `src/components/legal/{PrivacyPolicy,TermsOfService,ConsumerHealthData,MedicalDisclaimer}.tsx`, `src/components/consent/`, `src/components/dsar/`.

### Gap 2.1 — No state-specific privacy disclosures (CCPA/CPRA, CDPA-VA, CPA-CO, CTDPA-CT, UCPA-UT)
- **What:** `grep -rE "ccpa|cpra|colorado|cdpa|vcdpa"` across `src/components/legal/` returns **zero matches**. There is no CCPA "Do Not Sell or Share My Personal Information" link, no California-specific "rights under CCPA" section, no Virginia/Colorado opt-out language, no Connecticut/Utah disclosures. With 8 US states having operative comprehensive privacy laws as of 2026, an unauthenticated B2C SaaS launching nationally is in active non-compliance the moment a California resident signs up.
- **SEVERITY:** blocker (private right of action under CCPA = real exposure; consumer-watchdog reporting is automated)
- **EFFORT:** sub-phase (legal review + PrivacyPolicy.tsx state addendums + Do-Not-Sell footer link + opt-out form wired to a new `privacy_optout_requests` table + DSAR portal extension to handle state-rights flavors)
- **DEPENDS_ON:** existing v1.3 GDPR DSAR pipeline (extend, don't replace)

### Gap 2.2 — No accessibility statement page despite Phase 42 WCAG 2.2 AA work
- **What:** Phase 42 shipped a11y improvements + axe-core CI baseline (`tests/a11y/axe-baseline.test.ts`). No corresponding public-facing `/legal/accessibility` page exists. Clinic B2B procurement (especially state/federal clinics touching ADA-covered providers) routinely asks for a WCAG conformance statement. ADA Title III private-action exposure is real for a "place of public accommodation" SaaS.
- **SEVERITY:** hard-debt (Title III exposure is small but non-zero; B2B sales friction is the realer cost)
- **EFFORT:** single plan (`AccessibilityStatement.tsx` matching `LegalLayout` pattern + footer link)
- **DEPENDS_ON:** existing legal/* surface

### Gap 2.3 — Privacy policy + ToS update audit for v1.2/v1.3 features
- **What:** `PrivacyPolicy.tsx` was last meaningfully touched during Phase 22 GDPR work. Since then v1.3 added: PostHog Session Replay (Phase 24), Anthropic AI coach egress (extended), Mux video hosting for community (Phase 44), Stripe Connect for affiliates (Phase 19/26), clinic BAA chain (Phase 25), pgvector recommender pulling user-activity data (Phase 38), traffic-attribution recorder writing UTM + referrer (Phase 51). Each is a "we share personal data with new subprocessor / use it for a new purpose" event that legally requires policy update + notice. There is no documented audit confirming the privacy policy reflects all of these.
- **SEVERITY:** blocker (FTC Section 5 + state privacy AGs scrutinize "purposes not disclosed in policy" specifically)
- **EFFORT:** sub-phase (subprocessor list refresh — note Phase 25 has `subprocessor-diff` cron, USE that as input — + 8-section policy update + ToS update for community user-generated-content + record-of-changes timestamp + grandfathered-notice email to existing users)
- **DEPENDS_ON:** existing Phase 25 subprocessor-diff Edge Fn

### Gap 2.4 — DMCA / abuse / community-moderation public contact is unverified
- **What:** Phase 44-48 ship community feed + moderation tooling. DMCA Title II safe-harbor requires (a) a registered DMCA agent with the U.S. Copyright Office, (b) a publicly listed contact (`/legal/dmca` or similar), (c) takedown procedure. Need to verify: is there a `/legal/dmca` page? Is the DMCA agent registered? Same question for `abuse@leanshot.app` mailbox routing.
- **SEVERITY:** hard-debt (DMCA safe-harbor lost = LeanShot becomes liable for community-uploaded copyrighted content)
- **EFFORT:** single plan (register agent + page + mailbox route — mostly admin work, not engineering)
- **DEPENDS_ON:** existing Phase 44+48 moderation surface

### Gap 2.5 — Cookie banner WCAG 2.2 AA + state-mandated copy not verified
- **What:** Phase 22 shipped vanilla-cookieconsent v3 + Consent Mode v2. Hasn't been re-audited against WCAG 2.2 (which became operative June 2024 with new criteria) or state-mandated copy (California requires "Do Not Sell" surfaced in the same banner per CPRA regs).
- **SEVERITY:** hard-debt
- **EFFORT:** single plan (axe-core run against banner + CPRA copy injection)
- **DEPENDS_ON:** existing Phase 22 banner

## 3. Payment + revenue resilience

Audited against: `supabase/functions/stripe-{checkout,webhook}/`, `supabase/functions/_shared/email-templates/`, `supabase/functions/revenuecat-webhook/`.

### Gap 3.1 — Stripe Tax / sales-tax handling is absent
- **What:** `grep -rE "automatic_tax|stripe.*tax|tax_id_collection"` across `supabase/functions/` returns **zero matches** (one hit is `affiliates.tax_threshold_cents` — that's for affiliate 1099 thresholds, not customer sales tax). The stripe-checkout Edge Fn does not pass `automatic_tax: { enabled: true }`. As of 2026, every US state with sales tax + economic-nexus laws (45+ states) requires SaaS companies above modest thresholds (~$100K/yr or 200 transactions per state) to collect and remit sales tax. Most US states classify SaaS as taxable. Launching B2B + B2C nationally without this is direct accruing tax liability the day revenue starts.
- **SEVERITY:** blocker (state DOR audits + back-taxes + penalties are real; Stripe Tax retrofit during operations is painful — customers see retroactive tax line items)
- **EFFORT:** sub-phase (enable Stripe Tax in Stripe Dashboard + add `automatic_tax: { enabled: true }` + `customer_update.address: 'auto'` to all checkout sessions in `stripe-checkout/index.ts` + `tax_id_collection` for B2B clinic sessions + nexus-monitoring dashboard in `/admin/tax` + verify Stripe Connect payouts to affiliates aren't double-taxed)
- **DEPENDS_ON:** existing stripe-checkout (extends)

### Gap 3.2 — No dunning email sequence on `invoice.payment_failed`
- **What:** `supabase/functions/stripe-webhook/events/invoice-payment-failed.ts` correctly flips `ux_tier='past_due'` for Stripe-side dunning, but `ls supabase/functions/_shared/email-templates/` shows no `dunning-*` / `payment-failed-*` / `card-update-*` templates. Stripe's built-in Smart Retries handle the retry cadence but the **customer-facing email** ("your card was declined, update payment method here") is something Stripe sends only if Smart Email is enabled — and even then, the copy is generic and the link goes to a Stripe-hosted page, not the LeanShot in-app `/settings/billing` surface. The lifecycle Edge Fns (`lifecycle-behavior-triggered`, `lifecycle-retention`, etc.) do NOT have a `payment-failed-recovery` branch.
- **SEVERITY:** blocker (involuntary churn from failed payments is typically 5-15% of MRR for SaaS; the recovery email + in-app banner pair recovers ~50% of that — letting it ship without is leaving money + customers on the table)
- **EFFORT:** single plan (3-email dunning sequence T+1d, T+3d, T+7d + in-app `<PaymentFailedBanner>` + update-payment-method deep link + `dunning_state` column on subscriptions)
- **DEPENDS_ON:** existing lifecycle-* Edge Fns + invoice-payment-failed handler

### Gap 3.3 — Refund / cancellation / account-deletion self-service flows audit
- **What:** Account-deletion self-service exists (Phase 22 7-day-soft-delete). Cancellation self-service exists (Phase 40 save-offers). **Refund self-service does NOT exist** — admin tooling exists (`admin-stripe-action` Fn) but a user wanting a refund must email support. For a B2C wellness product launching nationally with possible FTC Restore Online Shoppers' Confidence Act (ROSCA) exposure + recurring-billing-cancellation state laws (California SB 313, Colorado HB 23-1234 et al), the "easy cancel" flow must extend to "easy refund within X days" disclosed clearly at checkout.
- **SEVERITY:** hard-debt (FTC ROSCA enforcement is active in 2026; the asymmetry between "easy to sign up" and "must email to refund" is exactly what ROSCA targets)
- **EFFORT:** single plan (self-service refund within trial + N-day money-back window + receipt-page CTA)
- **DEPENDS_ON:** existing admin-stripe-action Fn (downscope to user-callable RPC)

### Gap 3.4 — Stripe webhook idempotency under burst-retry not load-tested
- **What:** `stripe-webhook/index.ts` uses `subscription_events.event_id PRIMARY KEY` as idempotency anchor — correct pattern. RevenueCat webhook does the same. Neither has been tested under burst-retry (Stripe retries an event up to 3x with exponential backoff if the response isn't 2xx within 10s). The risk is at affiliate-conversion: `invoice.paid` triggers BOTH affiliate-eligibility insert AND ux_tier flip — if one succeeds and the function times out before the second, retry handling matters.
- **SEVERITY:** hard-debt (idempotency exists; "tested under burst-retry" is the gap)
- **EFFORT:** single plan (Deno test sending 5× same event_id in <1s + verify single-row outcome for affiliate-eligibility, ux_tier, and subscription_events)
- **DEPENDS_ON:** existing stripe-webhook (test-only addition)

## 4. Onboarding + activation + marketing readiness

### Gap 4.1 — No audience-specific landing pages (doctor / clinic / coach)
- **What:** `ls src/components/marketing/` shows ONE landing page (`Landing.tsx`). The product serves three audiences (B2C patient, doctor read-share, clinic/coach B2B) but the entire pre-auth marketing funnel is a single page. There is no `/for-doctors`, `/for-clinics`, `/for-coaches` or equivalent. Cold B2B traffic from clinics — the highest-LTV audience — lands on a patient-targeted page. Phase 15 page-builder COULD ship these as `landing_pages` rows (`page-render` Edge Fn already serves the publishing pipeline), but no plan has ever scaffolded them.
- **SEVERITY:** hard-debt (every dollar of B2B ad spend lands on the wrong page; conversion penalty 30-50% at minimum)
- **EFFORT:** sub-phase (3 landing pages via Phase 15 page-builder + footer/router wiring + audience-specific schema.org `Service` JSON-LD + sitemap inclusion)
- **DEPENDS_ON:** existing Phase 15 page-builder + Phase 51 attribution surface

### Gap 4.2 — Email-lifecycle dunning + win-back gap; transactional flows shipped, recovery flows partial
- **What:** Phase 22 shipped welcome-series + behavior-triggered + retention + transactional + preference-update lifecycle Fns. Reviewed templates: `community-*`, `csat-*`, `helpdesk-*`, `pause-*`, `sla-*` exist. **Missing**: payment-failed dunning (covered in Gap 3.2), trial-ending-soon (T-3 / T-1), inactive-user win-back (T+30 / T+60 / T+90), clinic-onboarding-stalled (BAA pending, billing not configured), and reactivation-discount campaign for cancelled subscriptions in the 30/60-day window.
- **SEVERITY:** hard-debt (every missing lifecycle email represents recoverable revenue; rough industry estimate is each well-tuned email = ~1% MRR lift)
- **EFFORT:** sub-phase (5 new email templates + 5 trigger conditions wired into existing `lifecycle-behavior-triggered` cron)
- **DEPENDS_ON:** existing Phase 22 lifecycle pipeline + Gap 3.2

### Gap 4.3 — No demo / sandbox mode for clinic-buyer prospects
- **What:** Clinic sales conversations need "click here, see what it looks like for 5 fake patients" without requiring the prospect to sign up + enter PHI. No demo/sandbox surface exists. v1.3 shipped clinic onboarding flow (Phase 31) but it requires real account creation. B2B sales cycle without a demo is a serious friction point.
- **SEVERITY:** hard-debt (B2B sales conversion penalty; not a launch-blocker but every clinic deal post-launch will request this)
- **EFFORT:** sub-phase (synthetic patient generator + `is_demo` flag on `organizations` + RLS deny for cross-tenant SELECT + auto-purge cron at 7 days)
- **DEPENDS_ON:** existing Phase 28-31 org schema

### Gap 4.4 — First-week activation milestone monitoring not wired to alerts
- **What:** Phase 34 shipped activation event + Phase 35 shipped XP/levels/streaks gamification. PostHog tracks the events. There is no automated alert if activation rate drops below threshold (e.g., week-over-week activation falls >20%). Phase 51 ships funnel analytics but the alerting layer is manual-dashboard-only. For a launch where you're spending on ads, you need to know within hours (not days) if a code change broke activation.
- **SEVERITY:** hard-debt (lose first-week launch revenue if a regression slips through; PostHog has built-in alerts but they must be configured per-funnel)
- **EFFORT:** single plan (PostHog alert config + Slack webhook for activation/payment/signup funnel breaks + runbook entry)
- **DEPENDS_ON:** existing Phase 51 + PostHog Personal API key (carry-over)
