<objective>
Close the D-07 audit gap surfaced by the Phase 40 planner: "User gets READ-ONLY access during pause. Existing data (charts, history, projections, AI coach history) remains visible. NEW logging (injection, weight, symptom, workout) DISABLED — clear UI banner: 'Your account is paused — logging resumes [date]. Resume now?'."

Phase 40 plans 40-01..40-06 ship the server side (subscriptions.is_paused mirror via 40-02, save-offer modal cancel-path via 40-04). None ship the dashboard-wide read-only gating. 40-04's success toast covers the ACCEPT path only — not the gate that prevents NEW logging across the dashboard while the user is paused.

This plan ships THREE concerns:
1. **Store-action hard backstop** — every logging action throws PausedSubscriptionError when is_paused=true. Even if a future UI surface forgets the soft disabled-state, the store refuses the write.
2. **Dashboard-wide banner** — single mount in AppShell with D-07 verbatim copy + Resume CTA reusing the 35-08 leanshot:open-settings event channel.
3. **Client-side state hydration** — extend billing-sync.ts (the single Phase 14 DB→store connector for subscription state) to read the 40-02-shipped columns and populate the new client slice.

Purpose: D-07 is the ONLY user-visible enforcement of pause semantics on the dashboard. Without it, a paused user can still log injections locally, which then conflicts with Stripe's no-billing-during-pause economic semantics (user keeps tracking, value-extracts during the pause). Worse: locally-logged rows queue in pendingOps and sync on resume, masking the intended "deliberate break" UX.

Output: 1 new error class + extensions to store/storage/billing-sync + 1 new banner component (with test) + 1 mount in AppShell + 1 store-guard test file. Wave 3 (after 40-02 ships the schema + webhook).
</objective>
